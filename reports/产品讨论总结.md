# 产品讨论总结

> 基于 pi-web-robin 的产品化讨论 · 2026-09-27

## 1. 起点

你想把 pi-web-robin（本地 agent 加 dashboard，有邮件、求职、研究等 workspace）抽出来，做成一个面向个人用户的产品。有三个问题还没想清楚：商业模式；agent 很难部署到云端；开源的话普通用户门槛太高。

## 2. 市场现状（2026 年 9 月调研）

- **完整形态还没有人做成。** "agent 建立并维护多个持久 workspace，后台定时更新"目前没有成熟产品，但每一块能力都已经有人在做：
  - ChatGPT Sites：agent 生成 dashboard 并定时刷新
  - Claude：artifact 存储加定时任务
  - Notion Custom Agents：仅限企业版
  - Google：Daily Brief 免费，Spark 是后台常驻 agent
  - Meta Muse：接入 Gmail 和日历，替用户执行任务
  - 开源项目 Hermes 的 Live Dashboard
- **大厂的共同弱点**：全部跑在云端；后台功能都要付费；产品反复推翻（Pulse、ChatGPT agent、Atlas 一年内全部下线）。
- **求职赛道**：付费意愿偏低，用户找到工作就流失。开源的 career-ops 很热门，但只能在终端里用。
- **Gmail**：读取邮件的权限都属于 restricted scope，面向公众上线需要通过 CASA 安全评估，约 $540–1,800/年，流程约 2 个月。早期可以用 100 人测试额度、IMAP，或让用户自带 OAuth client 绕开。

完整调研见 `reports/个人 agent dashboard 竞品调研.md`。

## 3. 需求判断

- **通用的个人 dashboard 需求弱。** iGoogle、Netvibes 都死了，Pulse 也被关掉：人们不会主动打开"又一个要看的地方"。
- **具体的痛点需求是真实的**：不错过重要的事、需要我决定的时候告诉我。
- 核心判断：**dashboard 当目的地没有吸引力；但如果它能替代用户每天去翻 N 个 app，就有价值。** 前提是覆盖得足够全，用户信得过。

## 4. 定位

- **目标用户**：需要长期追踪很多事的重度知识工作者，包括自由职业者、VC 和投资人、内容创作者、研究者、小生意经营者、非技术背景的高管。不追求覆盖所有人。
- **核心理念：in control。** 用户每天清楚该做什么、有哪些安排、长期目标推进到哪了。agent 负责维护和降低摩擦（自动加 todo、带链接直达要处理的地方、标出需要注意的事），决定权始终在用户手里。
- **一句话定位**：一个替你盯着所有事情、只在需要你拍板时才打扰你的 agent。

## 5. 产品核心：三个原语加一个 agent

1. **Pipelines（workspace）**：带阶段和下一步的记录。求职、CRM、deal flow、客户、内容选题、论文阅读本质上是同一个原语，换不同模板即可。**这是差异化的核心。**

   | 角色 | Workspace | 记录 | 阶段 | 下一步 |
   |---|---|---|---|---|
   | 求职者 | 求职 | 职位 | 发现 → 投递 → 面试 → offer | 投递 / 准备面试 |
   | VC | Deal flow | 公司 | 初筛 → 见面 → 尽调 → 决策 | 约第二次会 |
   | 自由职业者 | 客户 | 客户 / 项目 | 询价 → 报价 → 进行中 → 收款 | 发报价 / 催款 |
   | 做视频的 | 内容 | 选题 / 合作方 | 想法 → 脚本 → 拍摄 → 发布 | 回复品牌方 |
   | 研究者 | 阅读 | 论文 | 待读 → 在读 → 已整理 | 写笔记 |

2. **Goals**：3–5 个长期目标，事项挂在目标上，排序依据目标而不只是紧急程度。
3. **Today**：唯一的入口，汇总所有 pipeline 里到期的下一步，加上日历和需要处理的邮件。每一条都说明出现的原因、给出直达链接和建议的下一步。
4. **Agent**：从邮件和各个来源自动收集事项；用户可以用自然语言添加；事情办完后**自动关闭**；随时可以问问题。

**in control 要落实成的设计规则：**

- 每一条都能解释来源
- 不会悄悄丢东西（被忽略的可以翻看）
- 重要动作先提案再执行
- 所有操作可追溯、可撤销
- agent 的权限边界对用户可见、可设置

## 6. 和 Muse 等大厂的差异化

- **Muse 是跑腿的，我们帮人经营。** Muse 以"任务"为单位，办完就结束；我们以"持续推进的事"为单位，追踪几周到几个月。
- 站得住的差异化，按强弱排序：
  1. 数据归属和隐私：本地优先。VC、投资人、高管不会把机密交给 Meta。
  2. 持久的结构化状态：pipeline、阶段、CRM，而不是聊天记忆。
  3. 垂直深度：直连 ATS、行业数据源，用户自定义打分 rubric。
  4. 规则透明、可以纠正。
  5. 没有锁定：可以用自己的模型，数据就是本地文件。
- **只讲隐私卖不动**，必须配一个 Muse 做不好的具体工作流。
- 邮件分拣和每日摘要只是入场门槛，不是卖点。

## 7. 技术架构（从 Robin 抽象）

**Robin 里反复出现的模式：**

| Robin 里的东西 | 本质 |
|---|---|
| `*-domain.ts` 加 JSON 文件 | Collection：带约束的结构化记录 |
| `job-providers.ts`、`tech-event-sources.ts`、`gmail.ts` | Source：从外部拿数据 |
| scan → intake → rubric/score | Pipeline：拉取、清洗、去重、LLM 加工、写入 |
| `schedule.ts` 的 `runIfDue` + `delivery-ledger.ts` | Schedule 加 Delivery |
| `JobsBoard.tsx` + `usePolledResource` | View |
| `tools.ts` 的 allow-list + `runAssistantTurn(mode)` | Scoped Assistant |
| `job-profile.json`、rubric | Context |

**分层：**

```
┌──────────────────────────────────────────────────────────┐
│ Shell    桌面 app 窗口 · workspace 导航 · 引导 · 设置      │
├──────────────────────────────────────────────────────────┤
│ Assistant   自然语言维护：改记录 / 改 spec / 手动触发     │
│             工具由 spec 自动生成；改结构先提案、再确认    │
├──────────────────────────────────────────────────────────┤
│ Workspace = WorkspaceSpec（声明式）                        │
│   Collections · Sources · Pipelines · Views · Digests     │
│   · Context                                               │
├──────────────────────────────────────────────────────────┤
│ Kernel                                                    │
│   Store(带版本/撤销) · Scheduler · Run Log/Health          │
│   · Secrets · Agent Runtime(pi SDK) · Channels            │
└──────────────────────────────────────────────────────────┘
        ▲ 可插拔
   Connector 库（ATS、RSS、网页、Gmail/IMAP、Calendar…）
```

**关键原则：**

- Source（连接器）写成代码，其余都是配置。
- 处理不可信内容的 LLM 步骤只输出 JSON，由 kernel 写入，agent 没有任何写权限。
- Context 变更自动级联，比如改了 profile 会提示是否重新打分。
- 允许手写原生模块作为兜底。

**Robin 暴露出的缺口：**

- 大量手动 `.bak` 备份，说明需要变更历史和撤销。
- 多次静默失败，说明需要运行健康状态和主动告警。

这是面向普通用户的产品和个人工具之间最大的差别。

**现有代码的去留：**

- 直接搬进 kernel：`delivery-ledger.ts`、`schedule.ts`、`paths.ts`、`rpc-manager.ts`、assistant 的限定范围机制、`usePolledResource`
- 泛化：`store.ts` 和各 `*-domain.ts` 泛化成 Collection；`tools.ts` 泛化成自动生成的工具；`JobsBoard` 泛化成通用表格视图
- 做成 connector：`job-providers.ts`、`tech-event-sources.ts`、`google-calendar.ts`
- 留在个人版，不进产品：heat、urrag、capability atlas、neetcode、FSO

## 8. 形态与商业模式

**形态：**

- 桌面 app，推荐 Electron，可以直接跑现有的 Node/Next 后端。
- 和现在的"本地 Web 应用"本质上一样，只是加了安装包、常驻进程和自动更新。
- 只做 Mac 版约 3–5 周，Mac 和 Windows 都做约 6–8 周。
- 签名费用：Apple $99/年，Windows 约 $10/月起。

**手机端：**

1. Telegram 推送加回复（已有）
2. 中继远程访问，作为付费功能
3. 云端同步只读快照
4. 原生手机 app，往后放

**商业模式：**

- 纯开源门槛高；托管收入容易被第三方拿走（OpenClaw 的教训）。
- 倾向：开源核心、免费桌面 app，**付费买便利**（云端 runner、中继访问、内含 LLM 额度），同时支持用户自带 API key。
- **一次性卖源码不推荐**：会跑源码的人少，售后负担重，代码会腐烂，还容易泄露。更好的做法是卖打包好的 app，买断加一年更新（$29–49 起），或者按求职周期卖通行证。
- 附带发现：pi-web-robin 仓库目前是**公开的**，如果要卖就得先改成私有。

## 9. 主要难点

1. 后台任务静默失败，普通用户没法排查
2. 覆盖度决定信任：邮件和日历必须接入，Gmail 合规要尽早面对
3. 排序质量就是产品本身，排不准就是噪音
4. 数据源持续腐烂（网站改版、反爬、接口变化）
5. 安全：agent 会读不可信文本（邮件、JD），存在 prompt injection 风险
6. 冷启动：解决办法是首次使用时由 agent 访谈用户，生成第一批 workspace
7. 用户留存和 LLM 成本

## 10. MVP 和验证

**v0 范围：**

- Today：日历、需要处理的邮件、agent 收集的事项，全部带链接、带原因、能自动关闭
- Goals
- 一个 pipeline 原语，配两个模板：求职（你自己用）和轻 CRM（给朋友用）
- 自然语言收集和提问
- 访谈式引导
- Telegram 早晚两次推送

**v0 不做：**

- agent 从零创建任意 workspace
- 复杂视图
- 手机中继
- 云端 runner
- 模板市场
- 多用户

**架构是否成立的检验**：不改 kernel，只加一份 spec 和一个 connector，能不能做出第二个 workspace。

**需求验证**：10 个目标用户用两周，只看行为：第二周还有没有打开？有没有从推送直接行动？愿不愿意付 $10/月？

**自测信号**：你自己打开 dashboard 的次数，和从 Telegram 直接行动的次数，各是多少。

## 11. 待决问题

- 你朋友的角色和一天的工作流程是什么样的？（这是第二个验证场景）
- 你每天最常打开的 3 个外部地方是哪些？（这决定 Today 第一版必须接入哪些来源）
- 第一个目标人群选哪个：求职者，还是 VC/自由职业者？
- 商业模式最终走哪条路：买断 app，还是订阅便利服务？
