# Notes → Obsidian

Obsidian is the default permanent archive for Notes. Notion remains an optional destination.
This is a one-way, user-confirmed archive, not synchronization or a second Markdown editor.

## Use

1. Open a vault in Obsidian on the computer running Pi Web.
2. In `/notes`, choose that vault in the library. A single registered vault is selected automatically; multiple vaults require a choice.
3. Write a draft and attach images/PDFs. **Review & save** previews the original text without a model call. **Organize with AI** uses the existing preparation job instead.
4. Check the destination and preview, then confirm saving to Obsidian.
5. Continue editing the saved Markdown file in Obsidian. The Robin draft disappears only after publication and archive-index persistence succeed. The library retains recent archive links.

Choose **Notion** in the destination selector to use the existing parent-page selection and confirmed Notion archive workflow. Notion is not fetched by default.

## Notes / Canvas / Mind map

`/notes` now has the same inset, content-sized secondary navigation as Incoming and Job hunt. `?view=notes|canvas|mindmap` selects the workspace; old `?canvas=<id>` links still select Canvas. Switching flushes Canvas and refuses to unmount it on a failed save. Note draft state/autosave stays mounted through `useNoteDrafts` in `NotesWorkspace`; URLs retain chat context and browser Back/Forward restore the view. Canvas keeps its existing library, persistence and editor; merely opening its tab does not create a board.

The freeCodeCamp Python study board is a one-time Canvas import via `node --experimental-strip-types scripts/seed-python-study-canvas.mjs`: 17 reading/practice/answer rows, with answer cards to the right for self-check. The seed skips an existing board of that title, so it never overwrites personal edits. Learning Hub discovers the board through the Canvas list API and shows a deep link only when it exists; renaming or deleting the board removes that shortcut on refresh. Answers are not graded or tracked.

The **Mind map** tab is now an independent conversational editor, replacing the earlier note-outline projection. `?view=mindmap&mindmap=<uuid>` restores a document. New map creates a central topic; **Copy from Notes** explicitly copies the current note's ATX headings and nested lists, never changes or syncs the original. Prose/code/attachments are not imported; sources over 250 outline items refuse instead of silently truncating. Markdown export is a separate download. No graph layout or edits are written to Obsidian.

### Natural-language and manual editing

- A selected node (Ctrl/⌘/Shift-click for several, up to the full 1,000-node document limit) becomes an explicit reference beside the composer. **Select all / Ctrl/⌘ A** selects hidden topics too without expanding them; **Select this branch** includes its descendants. Buddy's scope block shows the current branch title, actual selection count and deduplicated descendant count; its native disclosure holds a bounded four-chip preview and Clear selection. Before inference, selected ancestors subsume selected descendants, so selecting the entire map sends the root as scope, not 1,000 redundant references. The native node selector also provides a keyboard/touch alternative to tiny zoomed nodes. The chat assistant receives the complete current map and last eight persisted conversation messages, not other maps or notes. Saved node explanations use the narrower source described below. **Edit map** can propose structural changes; **Discuss only** is enforced by the response validator and accepts no operations.
- `lib/mindmap-agent.ts` uses the chosen existing model through `runScopedAssistantTurn`: one-shot, `toolNames: []`, no filesystem/browser/MCP capability, medium thinking, no automatic turn deadline (`timeoutMs: 0`) and abort support. The model route declares no `maxDuration`; Stop/request cancellation still aborts generation, while other assistant scopes keep their existing deadlines. Labels/history are untrusted context. It returns a JSON proposal with `add`, `rename`, `link`, `move`, `remove` and `arrange` operations, not a whole-tree replacement. `arrange` balances main branches by subtree size, largest first, preserving all labels, IDs, sibling order and parentage. An optional `{id, side: "left" | "right"}` places that named root-level branch explicitly, even when the user selected a descendant. Only valid main-branch IDs and the two supported sides are accepted; discussion mode rejects arrangement too. The optional `branchSide` tree field is saved in the existing document snapshots and undo/redo; old trees without it keep their original alternating layout. No free-form coordinates, code or new tools are exposed to AI. New grouping/splitting preserves existing IDs by moving nodes. Model proposals normalize an omitted `children` field on new leaf nodes to `[]` before full batch validation; explicit null/non-array children remain errors. Stored trees and manual edit inputs remain strict. Other malformed output is rejected; it is never executed as code.
- The model endpoint **does not write**. The browser applies the validated proposal through the same PATCH as manual edits, including a base revision. Manual editing can continue during inference: a changed revision, unsaved node-text buffer or pending save refuses the late proposal. For an `arrange` proposal, a newer local drag/nudge/reset also refuses application; panning, zooming and selection alone do not. Cross-tab changes are checked again under the domain's lock. An unapplied answer is shown separately; resend after reconciling, never automatically rebase it.
- The canvas is a full-width plane, with a separate 24px-radius **Agent Buddy** window inset at the right, not a second grid column. Desktop Buddy width and the canvas camera reserve derive from a single numeric `--buddy-inset-open` token; keep the camera-facing `--buddy-inset` numeric (its reader uses `parseFloat`, not a CSS length resolver). The top toolbar groups node selection separately from detail/layout controls; the lower node toolbar separates manual actions from its accented explanation action. At phone widths the document selector and Buddy share the first header row, document actions use a second row, and the canvas controls use a compact two-column arrangement. Node toolbar width is intrinsic with a viewport bound, not the half-canvas shrink-to-fit width of a centred absolute element.
- Closing Buddy preserves chat draft/history; Escape and the minimize button return focus to its toggle. Opening it focuses the panel, **not** the textarea, so viewing a result does not request a mobile keyboard. Node explanations open their separate reader rather than expanding Buddy. **Change selection / Back to editing** closes Buddy and focuses the shared canvas locator or current inline editor, without saving or discarding it. On narrow screens Buddy overlays the canvas; on short screens it can scroll, with a sticky minimize header. Its scope block follows canvas selection; expanding it exposes reference removal without flooding the reading area. Message mode, explanatory mode hint, quick-prompt disclosure, model picker and Send/Stop share one composer. Quick prompts prepare but never send; they are disabled while an unsent chat draft exists rather than replacing it. Escape closes an open scope/prompt disclosure before closing Buddy.
- A running request immediately displays its pending message and captured scope/mode, separate from the current selection (which affects only the next message). Modes are disabled during inference; manual canvas edits remain possible with the existing stale-proposal guard. The header toggle shows Thinking even while minimized, then New reply until opened; this is local display state, not a new persisted notification ledger. A one-click explanation preserves both text and mode of an existing unsent draft. New replies scroll the message area by reply revision, including when the bounded history has reached 24 messages.
- Double-click or F2 edits a topic **in place**. Enter/Save commits; Escape cancels; Shift-Enter adds a line. Tab creates a child, Enter on a selected topic creates a sibling (a child for the root), arrow keys select nearby visible topics, Ctrl/⌘ Z and Shift-Ctrl/⌘ Z use the existing server history. Shortcuts are scoped to the canvas, ignore IME composition, and don't intercept typing; Shift-Tab leaves node controls. A native topic selector and visible Edit/Add actions remain non-drag alternatives.
- **Resource links**: each topic may have one optional `url`. Edit text or the link action opens the same inline draft with a labelled URL field; clearing it removes only the link. For new resources Buddy prefers separate child topics with `url` already attached; the user should not need to copy URLs from its reply into the field. Existing plain HTTP(S) URLs, angle autolinks and inline `[name](URL)` labels are also recognized at render time, including multiple resources in one topic. The original label is retained for editing/storage; display text shortens URL syntax and named resource anchors appear below it, deduplicated against the optional explicit URL. This recognition never mutates saved documents or guesses destinations from source names. Clearing the extra URL field does not remove URLs still written in the label. The shared validator reuses the link collection's URL normalization (bare hosts get HTTPS), then permits only HTTP(S), no embedded credentials/control characters, at most 2,048 characters per normalized URL and 100,000 URL characters per map. Node text and link changes commit atomically through the existing revision-checked batch; dirty drafts, failed writes and uncertain-receipt retries include both fields. Links survive reload, moves, undo/redo and Markdown export. A separate native anchor under the topic opens a new tab with `noopener noreferrer`, a full-URL tooltip/accessibility label and visible hostname; it is never nested in the topic button or a drag handle. Layout reserves a separate 44px row for each link; connectors and node controls stay aligned with the text area's centre. There is no preview fetch, favicon request or automatic navigation. AI may propose `link` with `url:null` for removal or optional `url` on added nodes, but remains tool-free and cannot attach links in discussion mode. Source requests must include named Markdown hyperlinks in the reply and actual URL fields/operations for map edits. Supplied/existing URLs are preferred; confidently known official homepages may be suggested as unverified, but unknown deep paths/channel/video URLs must not be fabricated. Buddy's persisted replies, user messages and unapplied proposals render lightweight Markdown/GFM with HTTP(S)-only native new-tab anchors. Raw HTML, images, executable/app schemes and local paths are not enabled; the shared Markdown CJK-autolink correction keeps Chinese punctuation/prose outside URLs. Discussion may contain clickable links in the reply without editing the map.
- **Explain branch** opens the independent **Node explanations** reader described below. Existing documents use **Read explanation** instead and never automatically regenerate. Buddy's scope action uses that same reader for one selected branch (selected ancestors subsume descendants); no selection means the current focused branch (or the whole map outside focus). Disjoint selected branches require choosing one, with a visible hint rather than silently binding a combined reply to an arbitrary node. Ordinary chat replies remain in Buddy, with Markdown downloads; their historical text is not guessed into node-bound documents.
- The floating selection/layout toolbar does not lock merely because an inline editor is open. Choosing a node, Select all, detail level or Reset positions first commits that draft and proceeds only on success; empty text, invalid links and failed saves retain both the draft and previous selection. Select all includes a newly committed topic. Tidy layout batches the draft edit and arrangement into one atomic, undoable write. An editing notice and Cancel edit stay on the toolbar even if panning hides the editor. Explicit detail changes after saving run after automatic changed-node reveal, so the save cannot silently undo the chosen fold level. Saved/retried edits do not automatically replay a failed view action. Editing camera reveal reserves the toolbar's actual height.
- A new topic is a local draft, not an empty server record: cancellation writes nothing. Failed saves retain the editor; a successful explicit retry closes it only when the acknowledged revision contains its text. Selection changes first try to commit an active draft and refuse on failure. Hiding the Notes tab preserves it without saving. New maps use an inline title form, not a browser prompt; deletion still explicitly confirms.
- Node dragging uses pointer capture with a 6px threshold, not native HTML drag-and-drop: the actual node, visible descendants and connector endpoints follow mouse/touch movement at the current zoom. After offsets are applied, each edge derives its left/right direction from the current parent/child centres, not the automatic layout's original side; crossing a parent flips both connector anchors and the node's outward add/fold controls during dragging and after reload. Crossing alone never changes parentage. Drop on empty canvas to position a branch; drop on a highlighted valid parent to reparent through the existing revision-checked write. Root dragging moves the whole diagram but cannot reparent it. Pointer cancellation, Escape, window blur, hidden workspace and concurrent tree changes cancel the preview; failed reparenting restores the pre-drag layout. A drag release never becomes click-to-zoom or text editing. A drag starting on any selected topic moves all selected branches together. Ancestor/descendant selections are reduced to disjoint roots, avoiding double translation; selecting the whole map translates the root only, including folded descendants. Group reparenting is one atomic batch, capped at 100 disjoint branches by the existing operation limit; the root never reparents. More → parent selector remains the single-branch non-drag structural alternative; Alt+arrows nudge the entire selection.
- Free positions are view-only offsets inherited down the tree, scoped to `pi-mindmap-layout:<document UUID>` in this browser's localStorage. They are not synchronized, included in content undo/redo, or sent to the model. Reset layout clears only those offsets, not topics, relationships or content history. **Tidy layout** calls the same persisted `arrange` operation as Buddy, without a model call. It resets local offsets only after a successful save (including explicit retry), then fits the current detail level; failures preserve positions. Restoring a different saved side assignment with undo/redo also clears conflicting local offsets. Undo restores branch sides, not the previous browser-local free positions. Left/right actions in More offer a manual alternative. **Ask Buddy to tidy** lives in the composer's Quick prompts disclosure, including with existing chat history, and prepares an explicit non-destructive layout prompt; it does not auto-send or replace a nonempty draft. The canvas's Tidy layout remains the immediate, model-free action. Restored offsets must be finite/bounded and match the node's current parent; reparenting ignores the old parent's offset. Browser storage failures keep the current layout in memory and show a warning. Fit accounts for moved nodes, including negative coordinates. Fold and all camera changes are view-only. **Main branches / Two levels / All details** gives dense maps an explicit outline control and fits the chosen level. Maps over 60 topics initially show two levels; a single update adding more than 30 topics returns to that overview rather than exposing hundreds of boxes. Counts show visible/total topics; nothing is deleted. Selecting a folded topic does not expand it; the locator unfolds only ancestors needed to reveal its target. The viewport uses a translate/scale camera: drag background or scroll to pan, Ctrl/⌘-scroll to zoom under the pointer, two background pointers to pinch, +/− and Fit as alternatives. First open favours readable text (at least 85%); Fit explicitly shows the whole map. Selecting through the locator reveals a readable topic. Layout changes preserve the root's screen anchor, and focus/fit allow for the floating Buddy's footprint. Topic width follows label length; main branches keep their alternating or saved left/right assignment on text edits and folding. Automatic layout budgets visible subtree area (including long labels and resource rows) against a roughly square footprint. Dense children wrap into outward columns, with whole subtrees above/below a clear horizontal connector corridor instead of one tall list. Root packing compares actual subtree footprints so it does not merely turn a tall map into a wide strip. When main branches fit in one column on a side, four or more fan along a soft oval envelope, with centre branches farther out and outer branches closer in. Rounded connector turns use the column gutters and are recomputed with dragged endpoints. Small branches retain the simpler single-column fan; this is compact rectangular-topic packing, not a force simulation or text rotated around a perfect circle. It is deterministic and view-only: IDs, order, parentage, saved sides and undo stay unchanged; existing local drag offsets still apply, and Tidy layout resets them as before. Depth-two and deeper topics use a complete 2px branch-coloured border, 12px rounded corners and a faint opaque tinted fill, not an underline-only treatment. Their border mixes the branch colour with theme text so it remains distinct in light and dark palettes; the browser regression checks all four sides and at least 3:1 contrast against the node fill in Glass, Dark glass and Light. Changed topics have a small dot; selection has a separate outline. Full long labels remain in accessible names, tooltips and the editor.
- Undo/redo restores content snapshots with a new revision (up to 20); conversation remains historical and each message shows its revision. Tab switches hide rather than destroy this workspace, preserving drafts and in-flight replies. Chat drafts are best-effort browser-local; unsaved node text is held in memory with a navigation/unload warning, not crash recovery. Storage failures keep local input and explicit retry. Stop cancels an unapplied model proposal, not a PATCH already sent; the UI says so.

### Branch focus

- Select any non-root topic and choose **Focus branch** in its toolbar. This renders the original node and descendants as a temporary view root, initially fully expanded at readable scale; it does not clone a tree, create a document, or write a content revision. Double-click remains text editing. The breadcrumb row offers **Back to whole map** and each ancestor; long labels truncate with full-title tooltips, and the row scrolls on small screens.
- One renderer is mounted at a time. In-memory snapshots retain each view's camera, folds, selection and free positions until the document is closed/reloaded. Returning restores the previous view without selecting/revealing a different node. Focus free positions do not overwrite the whole map's existing browser-local positions. Phone rotation/window resizing preserves the reading centre. Whole-map layout/side controls are omitted in focus because their persisted operations apply to document-level branches, not temporary view children.
- The locator, Select all and keyboard selection operate on the focused subtree, including folded descendants. With no selection, Buddy and its explanation action default to that complete branch; choosing a descendant narrows the next request. Ordinary chat still receives the full map as background context and the original selected IDs, under the existing scoped prompt; this is not an enforced permission boundary. An in-flight request keeps its captured scope when the reading view changes.
- Edits, adds, moves within the view, links, explanations and undo/redo use original document IDs and the existing revision-checked writes. The focus root cannot be removed/reparented from its own view; return to its parent to do so. Breadcrumb navigation first commits a draft and refuses on empty text, invalid URL or save failure; explicit retry retains the draft and does not automatically replay navigation. If undo or a refreshed document removes the focus target, the view falls back to the whole map. Focus is not stored in the URL or restored across reloads.
- `mindmapPath()` tests original-node identity, nested paths, reparenting and removed-target fallback. The fixture browser test covers hidden siblings, unfolded descendants, scoped selection/Buddy requests, nested breadcrumbs, exact camera/fold restoration, isolated view positions, failed draft saves/retry, original-document undo, deleted-focus fallback and 320/375px controls. No personal maps or live models are used.

### Saved node explanations

- The map header's **Node explanations** opens the saved-document library without calling a model. The node toolbar's **Explain branch** opens it and generates only if that node has no saved explanation. Afterward it becomes **Read explanation**. Each map/node ID owns one latest document; overlapping branch summaries are independent. Reader selection does not change canvas selection or chat drafts/modes. Deleted nodes keep their saved text in the library, labelled **Node removed**; regeneration is disabled until that node is restored. Deleting the whole map deletes its explanations too.
- Desktop uses a native modal reader up to 1,180px wide, with saved documents alongside a continuous reading surface; phones use the full dynamic viewport and a compact horizontally scrollable document list. The document scrolls separately from its always-reachable close header. Escape returns to the opening control; focus initially lands on Close, never a text field. There are no new animations, dependencies or editor instances. Markdown/GFM headings, lists, quotes, tables and code render with 17px-minimum UI body type; code/tables have keyboard-focusable overflow areas. HTML, remote images and non-HTTP(S) links remain disabled. **Download text · Markdown** exports the exact body.
- Generation covers the node and **all** descendants, including folded topics. Only the direct parent's topic and immediate sibling topics (IDs, labels, links, not their descendants) provide nearby context. The `explain` request to the existing model endpoint uses a separate document prompt, the same chosen model/tool-free runner, and **no chat history or unrelated deep branches**. It is enforced as `operations:[]` and never changes tree content. Missing model selection offers a return to Buddy's model picker; unsaved/uncertain canvas edits or a running Buddy request block generation but not reading saved text.
- `mindmap-explanation.ts` defines the exact source used both for the model and SHA-256 freshness. Labels, links, child structure/order and immediate parent/sibling context are included. Layout sides, camera, free offsets, fold state, chat messages and deeper changes in unrelated branches are not. The source is read from the current saved tree, never reconstructed from visible topics. A changed source displays **Map updated** with **Regenerate explanation**; matching source after undo becomes current again. Freshness is checked on open, after this tab's writes, or with **Check for updates**; there is no background regeneration or poll. Full-map explanations naturally depend on all content.
- Regeneration is explicit and keeps the previous saved document readable while running. Only a successful atomic save replaces it. Stop/close aborts generation; a PATCH already sent can still complete. Failed or uncertain saves keep the new Markdown as a clearly **unconfirmed** preview with download and an exact-payload **Retry saving**, without spending tokens again. Closing/switching/refreshing an unconfirmed preview asks before discarding it; unload warns. A revision conflict preserves the stored document and requires checking updates and explicitly generating again, never silently rebasing an old explanation. An uncertain retry reads the actual current saved body, so a late receipt cannot mislabel a superseded preview as the newest version.
- Documents are an optional `explanations` array in the existing private version-1 map file. Older maps open with an empty index; existing chat replies are unchanged. Each record holds `nodeId`, generated title, Markdown (up to 12,000 characters), `sourceHash`, `sourceRevision` and `generatedAt`. At most 1,000 documents per map, including removed nodes, are retained; limits fail explicitly rather than evicting saved text. Saving is the isolated `explain` PATCH action with the existing revision/request-ID checks; it cannot include tree operations or conversation. It increments the document revision but neither consumes tree undo history nor clears redo, and is independent of the 24-message chat bound. Ordinary map GET/PATCH returns only the small document index (current title, timestamp, provenance, stale/missing flags); `GET ?id=…&explanation=<nodeId>` reads the requested body and current index on demand. Malformed explanation storage fails closed.

### Persistence and implementation provenance

`extension/robin/mindmap.ts` owns the tree/edit contract; `mindmap-domain.ts` owns `mindmaps/<uuid>.json`, outside the task SQLite migration. Each private atomic file holds the version-1 tree, revision, 24 recent chat messages, undo/redo, optional node explanations and the last 50 mutation receipts. A client-generated document UUID makes uncertain creates retryable. The same mutation ID and payload can be retried without duplicate application; reusing the ID for a different payload is rejected. Receipts are bounded, not an unlimited exactly-once guarantee. Deletes and edits check revisions under the same file lock; late writes never recreate deleted maps. Corrupt/newer files fail closed.

The entire operation batch is validated on a copy before commit: no unknown IDs, duplicate IDs, cycles, root removal/move, unsupported fields/actions or invalid positions. Bounds: 1,000 nodes (including the root and folded topics), 16 levels, 500 characters/label, 60,000 total label characters and 100 operations/batch. Node-count and total-text failures report the specific exceeded limit; neither truncates data. The model's limit instructions interpolate the shared validation constants. HTTP adapters use the shared origin/content-type guard and bounded bodies (512 KB CRUD, 128 KB model request, accommodating 1,000 long IDs plus multilingual labels/instructions). The separate Notes outline import remains capped at 250 items. Raising the node limit does not remove the text/context budget.

## Draft autosave before archiving

`useNoteDrafts` owns the mounted draft collection and text-write lifetime:
400 ms debounce, one serialized PATCH queue, exact edit identity, local recovery,
per-draft status/error and delete/archive ordering. `NotesWorkspace` remains the
adapter for loading/creation, navigation, confirmation, archive destinations and
post-archive UI. Canvas, attachments and finalization retain their own modules.

A failed save is retried only if that exact draft is still current; a newer edit
may already have left the pending slot and entered the write queue. Requeueing an
obsolete failure can overwrite a newer successful save during pagehide. Save
status counts queued/in-flight writes, not just the pending slot: an earlier
receipt cannot mark a later write saved. Errors and retries belong to the selected
note; switching drafts cannot carry another note's save error into a clean editor.

Delete and archive freeze that note's edits and retries before awaiting the queue.
Delete discards unsent debounce work, but restores unconfirmed text for explicit
retry if deletion fails. Archive flushes first and refuses publication unless the
latest text is acknowledged. Both retain the local draft until the operation
succeeds; late failures/background flushes cannot PATCH a deleted draft. The caller
still confirms deletion or destination/content before invoking either operation.

Pagehide, hidden-document and unmount flushes remain best effort. Keepalive is used
only for serialized UTF-8 bodies up to 60,000 bytes; larger text is sent intact
without keepalive. This is not a guarantee that mobile shutdown delivers requests.
This protects this tab's write ordering, not concurrent editing from other devices.
[Local text recovery](text-recovery.md) separately backs up title/text/destination at
edit time, offers manual preview/restore/discard after reopening, and clears only
acknowledged revisions. Storage is bounded and best-effort; attachments and canvas
are not included, and a local copy never silently overwrites the server version.

Checks: `components/robin/useNoteDrafts.test.mjs` uses controlled transport and real
recovery functions at the module interface. `e2e/notes-autosave.mjs` mocks queued
receipts, failure/retry, draft switches and deletion interleavings;
`e2e/obsidian-notes.mjs` covers confirmed archive and failed-flush refusal;
`e2e/text-recovery.mjs` covers reopening and cross-tab recovery. No check publishes
a real note or calls a model (the archive E2E's initial vault discovery is read-only).

While AI finalization runs, the browser's 2.5-second status poll and one-second
elapsed clock stop when the document is hidden. Returning refreshes status and
resets the clock immediately; finishing/unmounting removes both timers and the
visibility listener. This does not cancel server-side finalization. A read already
in flight can finish while hidden. `e2e/background-polling.mjs` verifies timer removal,
request counts, recovery and completion with mocked data. Each read advances the
same generation used by local finalize/cancel/discard updates; an older poll cannot
replace a newer ready result or undo a local command. Unmount invalidates reads.

Attachment removal retains the row until DELETE succeeds. Its control is disabled
while that file's request is pending, guarded against duplicate submission, and
available again on HTTP/network failure. A confirmed removal invalidates earlier
attachment reads for that draft; reads from departed visits are also ignored.
Upload receipts invalidate earlier lists too, and upsert by attachment ID: a GET
may already contain a file before its POST response arrives. Do not append that
receipt twice or let a pre-upload snapshot erase it. The same browser fixture
covers both response orders, including Strict Mode's duplicate initial reads.
File notices are scoped to the initiating note. The delete target is 44×44 CSS px
on narrow or touch-capable screens, with visible keyboard focus. This is verified
in browser emulation, not a physical-phone check. `e2e/frontend-reliability.mjs`
covers failure/retry, obsolete reads, finalization ordering and touch-target size;
all business endpoints are mocked.

The Obsidian search adapter returns literal status discriminants (`searched` versus
`ready` / `choose-vault` / `no-vault`) so callers may safely narrow before inspecting
scan limits. This is a type contract only; vault discovery and permissions are unchanged.

## Files and discovery

Vault discovery reads Obsidian's `obsidian.json` in the platform configuration directory:

- macOS: `~/Library/Application Support/obsidian/obsidian.json`
- Windows: `%APPDATA%/obsidian/obsidian.json`
- Linux: `$XDG_CONFIG_HOME/obsidian/obsidian.json` or `~/.config/obsidian/obsidian.json`

`ROBIN_OBSIDIAN_CONFIG` can override the registry path for operator configuration and isolated tests. HTTP requests supply a registered vault ID, never an arbitrary filesystem path. Existing vaults must contain `.obsidian`; the integration does not create or modify Obsidian configuration.

Each archive is a self-contained bundle:

```text
<vault>/Notes/Robin-<draft-id>/
  <sanitized-title>.md
  Attachments/<attachment-id>-<original-name>
  .robin-archive.json
```

Stable draft IDs avoid title collisions. A hidden staging directory is renamed into place only after all original attachment bytes, Markdown and the recovery receipt have been written. `attachment:ID` Markdown links become local relative links; attachments not referenced in the body are appended. Unknown/missing attachments fail the archive rather than silently disappear. Obsidian edits are never overwritten by retries.

Robin records archive receipts in `~/.pi/robin/obsidian-archives.json` (or `ROBIN_DATA_DIR`). A published bundle's hidden receipt allows retry recovery if the Robin index write fails. Draft text and attachment IDs are checked against the reviewed snapshot, and writes are serialized with draft/attachment changes. Symlinked archive directories and unrelated pre-existing bundles are refused.

Research's **Keep in notebook** is an explicit one-click archive action: it saves the selected stored answer to the project notebook and uses this same publication mechanism to create an Obsidian note. One registered vault is auto-selected; multiple vaults require the user's choice in the project notebook. The project remembers that choice, and per-message receipts make retries/reloads safe. A vault failure preserves the notebook and offers a retry; no separate preview or model step is required for each Keep click. See [Research workspace](research-reading-room.md#keep--automatic-obsidian-archive).

No automatic migration of existing Notes, Product ideas, FSO notes or Notion pages occurs. Task status, progress and product stages remain in Robin. The separate `/obsidian` workspace browses current files; it does not provide two-way editing. Archive links are creation receipts, not a live file index: renaming or moving a file in Obsidian does not update an archive receipt.

## Conversation → linked knowledge

The conversation toolbar's **Capture knowledge / 沉淀到知识库** action is a separate workflow from draft archiving. It never deletes a draft or modifies the source session.

1. Select the current branch's entire conversation, last 12 text messages, or last 4. Check the expandable source before sending it to the chosen model. Sources over 80,000 characters are refused, not silently truncated.
2. Choose the registered vault, project name and model. Only user/assistant text from that ancestor chain plus a bounded catalog of vault filenames is sent. Thinking, tool results, system/custom messages, images, sibling branches and existing note bodies are excluded. The catalog skips hidden/symlinked entries and stops at 200 Markdown files or 5,000 directory entries.
3. A tool-free, one-shot model call proposes 1–5 ideas, decisions, architecture notes, progress snapshots or summaries. Suggestions must remain distinguishable from confirmed decisions; reported progress is not verified live state. Model output can cite known message/note IDs, never choose arbitrary filesystem paths.
4. Review each new note or append-only supplement, its destination, project entry page, explicit `[[links]]`, provenance and (for supplements) the unchanged existing text. Confirmation saves the stored proposal, not a second generation. The first version saves all proposed notes together; go back and prepare again if the proposal is unsuitable.
5. Open saved notes in Obsidian, or find their links in Notes' existing archive list. Native backlinks and Graph View connect them through the project entry page and suggested relationships. The separate `/obsidian` browser can also visualize these explicit links; neither workflow introduces a graph database.

New files are placed under:

```text
<vault>/Knowledge/<sanitized-project>-<stable-hash>/
  Project.md
  <capture-id>/
    n1-<title>.md
    n2-<title>.md
```

A model may propose a supplement to a cataloged existing file instead. Its body is read **locally** for review and hash-checked again at confirmation. New files are published without replacement; supplements append to the checked file descriptor. Existing project entry pages are never replaced. Notes include a conversation URL, branch ID, supporting message IDs, capture timestamp and scope. The URL opens the conversation; the branch ID records which branch was actually used, rather than claiming the URL restores an immutable transcript.

`knowledge-proposals.json` in `ROBIN_DATA_DIR` holds review/retry state, generated Markdown and existing-text snapshots, not a second editing surface or the raw source transcript. It may contain sensitive reviewed text, so protect it with the rest of Robin's data. The same source fingerprint/project/vault reuses its previous proposal unless the user explicitly prepares again. The toolbar shows the saved-note count; the dialog lists recent proposals and their saved/total counts. Partial success is reported and retained; completion markers allow retries after publication without appending twice. A changed existing note requires a new preview. A source conversation remains unchanged even if preparation fails or is cancelled.

Local locks serialize Robin writers, **not Obsidian or other filesystem clients**. Hash/inode checks detect changes around the append, but cannot make simultaneous external editor saves transactional. Avoid editing the same target during confirmation. Robin still does not track subsequent Obsidian moves, renames, deletions or edits.

Implementation: `lib/knowledge-source.ts` owns branch selection; `extension/robin/knowledge-domain.ts` owns proposals/publication; `app/api/sessions/[id]/knowledge/route.ts` supplies the HTTP and model adapter; `components/KnowledgeCaptureDialog.tsx` owns the review flow.

## Local vault workspace (`/obsidian`)

A dedicated **Obsidian** navigation entry opens a read-only view of the same registered vaults. A single vault is selected automatically; multiple vaults require a choice. The existing Notes/archive workflow is unchanged.

- **Library** (default): note cards with a bounded 240-character plain-text excerpt from the current file, directory colour, modification date and unique-neighbour count. Excerpts are local text, not AI summaries; no additional file/model requests are made per card. Search filters titles/paths; collection filters select the top-level folder, linked notes or unlinked notes. Sort by recent modification, title or connection count. The collapsible file directory remains an alternative. Cards open a side preview; **Read full note** opens the document. Selecting a note updates `?vault=…&note=…&view=…`, preserving chat context; reload restores note, vault and view (not filters or camera).
- **Glass ground**: the workspace shell and library's space between cards opt into shared `.robin-workspace-ground`; no independent page wash. Cards, full reading, graph canvas, inspector and sticky reader header keep their reading backgrounds. Other palettes are unchanged. `e2e/workspace-ground.mjs` compares the shared source across five workspaces.
- **Reading surfaces**: library cards and the separated workspace panes use the shared 16px card radius; controls and code/table frames use 8px. The desktop node preview is 320–440px wide and scrolls with the inspector, not inside a second height-capped body. Preview text is 16px and full reading text 18px (rem-based), with system fonts, main-text contrast, upright semibold headings and room between paragraphs/lists. Full reading gives the former file-column space to the document and keeps connections alongside it; return to Library/Graph for collections. Code and tables have keyboard-focusable horizontal scroll regions, not clipped content or page-wide overflow. Mobile keeps one visible pane, with the same typography and theme tokens.
- **Reader**: Markdown/GFM, hidden front matter, supported wikilinks (`[[note|label]]`, including note-embed links) and inline Markdown note links. Code and HTML comments are excluded from link extraction. Relative paths and exact vault paths are resolved before unique short names; ambiguous names remain unresolved. Same-note heading navigation is supported; cross-note links open the destination note, not a guaranteed heading/block position. Reference-style Markdown links, YAML aliases, block references, Dataview, Obsidian `.canvas` boards, plugin views and transclusion are not emulated. The original Markdown is available in a source fold.
- **Preview and connections**: a card/node opens the actual Markdown in the inspector alongside outgoing links, backlinks and unresolved links, without leaving the library/graph. Links from front matter are included when written as wikilinks. These are syntactic relationships, not AI-inferred associations. Mobile switches between collections, workspace and preview; preview text is not clipped behind a nested scroll on phones.
- **Canvas Graph**: replaces the old 80-node SVG with all indexed notes (up to 1,000), using the already-installed `d3-force` package now declared directly. Folder colour is consistent across cards/filters/nodes; radius reflects unique neighbours. Reciprocal links share one visual edge while the reader preserves direction. Whole-vault, one-hop and two-hop scopes intersect the current title/path and collection filters. The force layout uses repulsion, collision, links and a gentle folder attraction; it is not a semantic/AI clustering model. Dense rendering/force work is capped at 10,000 unique edges with a visible notice; adjacency, scope and counts still use all indexed links.
- **Graph interaction**: wheel/trackpad zoom is anchored under the pointer; drag empty space to pan, drag a node to pin its position, hover to highlight its neighbours, click to preview and double-click to read. Two-pointer pinch scales and pans without selecting a node. Locate a note through the native selector, use +/−/Fit/Re-layout buttons, or focus the canvas and use arrow keys, +/−, 0 and Enter. Re-layout releases pins. Focus canvas hides the sidebars; Escape restores them, and selecting a node reveals the preview again (including on phones). File/cards/connection lists remain the accessible alternative to the Canvas drawing.
- **Graph lifecycle**: lazily loaded Canvas module with DPR capped at 2; semantic theme colours are refreshed when the theme changes. Force computation runs in bounded requestAnimationFrame slices, stops when settled and pauses when hidden/inactive. Reduced motion computes the layout without showing intermediate frames. Pointer capture ends/cancels safely. Selecting a note does not rebuild global graph data; switching between library, graph and reader preserves the mounted graph's camera and positions. Vault switches remount it. Filter changes reuse known positions; refresh/reload may reset the graph. No layout positions or pinned nodes are written to the vault.
- **Refresh**: rereads current files and links, including external edits, renames and deletions. There is no persistent browser index, filesystem watcher, automatic model call, write endpoint or second copy of the vault. **Edit in Obsidian** opens the original file through `obsidian://`; it requires that vault on the browser device.
- **Privacy and bounds**: only registered roots; no hidden paths, symlink entries, arbitrary server paths or non-Markdown content. Reads use no-follow/non-blocking file descriptors, bounded buffers and post-read checks. The index stops at 1,000 notes, 20 MiB of Markdown, 20,000 directory entries or depth 32; individual notes are capped at 256 KiB and indexed relationships at 200 per note. Partial/skipped results are visible, never represented as a complete vault. External image requests and raw HTML rendering are disabled; attachments stay in Obsidian. API responses are private/no-store and use the shared origin/auth boundary. Local filesystem clients can still race traversal; this is not an OS sandbox against a malicious process with write access to the vault.

`extension/robin/obsidian-browser-domain.ts` owns read/index boundaries and card excerpts; `obsidian-links.ts` owns the shared supported-link subset; `/api/robin/obsidian/vault` is a GET-only adapter. `components/robin/obsidian-graph.ts` owns adjacency, bounded graph construction and camera/hit-test math; `ObsidianGraph.tsx` owns the Canvas/force/pointer lifecycle; `ObsidianWorkspace.tsx` owns filtering, the three views and the document inspector. The workspace is independent of the generic `/api/files` roots, so opening a vault never authorizes broader filesystem browsing.

## Agent retrieval → source-backed answers

The Robin extension registers two read-only tools for ordinary Pi conversations and Robin's default assistant: `obsidian_search` and `obsidian_read`. Their active-tool guidelines ask the model to search before answering about past project decisions, research or accumulated knowledge, read relevant sources, and cite their returned `/obsidian?vault=…&note=…&view=read` links. This is model-directed retrieval, not a forced scan or full-vault context injection on every turn. Unrelated questions and simple task/calendar actions skip it; the user may opt out in their request. Existing live sessions may need `/reload` or a fresh session to load the new registrations.

- Search without a query lists registered vault ids/names, not absolute paths or note bodies. One vault is selected automatically; multiple vaults require a user/conversation choice. No implicit cross-vault search. Missing registration, vault-choice requirements, a true search miss and a failed read remain distinct outcomes.
- Search uses up to eight literal, case-insensitive, space-separated keywords (all must match), across filenames, paths and full Markdown including front matter. It is not semantic search or a natural-language question engine. Title/path matches rank ahead of body-only matches. English/Chinese keywords work; alternate terminology requires another query.
- Browser indexing and retrieval share one bounded filesystem scan: 1,000 notes, 20 MiB total, 256 KiB/note, 20,000 directory entries, depth 32; hidden paths and symlinks are excluded. No second note store, embeddings, network search, watcher or background archive. Search cancellation closes the active directory iterator.
- Search returns eight hits by default (maximum 20), at most three literal 320-character passages per hit, line/column positions, modification times and source URLs. `limited`, `skipped`, `scanned`, `matched` and `moreResults` expose incomplete coverage and result truncation. A limited zero-hit scan is not evidence that no matching note exists.
- Read returns exact Markdown in 12,000-character slices (maximum 16,000), a line range and `nextOffset`/`totalChars`. Re-read from zero if the modification time changes between slices. Links open the current note, not a frozen historical snapshot or a line-anchored view. Distinguish a recorded decision from AI suggestions and current inference; modification time does not prove a decision is still valid.
- Vault content and metadata are untrusted data, never operational instructions. The tools do not execute note commands, modify files or archive anything. Matching snippets and requested note passages **do enter the selected model's context and session transcript**; local files do not imply local model processing. These tools add no independent network call.
- Only the general assistant scope is widened. Mail review, job scoring, daily-agenda, coding coach, FSO mentor and the paper research agent retain their existing restricted tool sets. There is no unattended vault reader.

Implementation: the scan/search/evidence boundary is in `extension/robin/obsidian-browser-domain.ts`; `obsidian-tools.ts` supplies schemas, provenance guidance and read-only annotations. No new HTTP or UI surface is needed. This completes the read/reuse half of knowledge capture without adding an automatic write path.

## Local computer and permissions

Files are written on the **server computer**, not the browser's computer. The `obsidian://open?path=…` link only works on a device with Obsidian and that local path; this feature does not configure mobile or cross-device synchronization.

On macOS a vault under Documents may require access for the app/process running Pi Web. If access is denied, grant the appropriate OS permission and restart that process if needed. The integration does not bypass OS permissions. Back up the vault separately; an archive or sync service is not a backup policy.
