# Jobs application automation

The user-approved workflow is **Jobright Autofill → audit against approved sources → repair → submit if all checks pass → confirm receipt**. Jobright is the initial filler, not a source of truth. Routine omissions are the worker's job, not a mandatory manual-review handoff. Attention is for genuinely unknown personal facts, permissions or account access; technical failures have a separate status. Never call an attempt a successful application.

## Authorization and trust

- Default scheduling and automatic submission are off until deliberately configured. `submissionPolicy: "jobright-trusted-v2"` records this user's scoped approval to retain Jobright-populated answers, including legal declarations, and audit only missing fields. Enabling the schedule alone does not grant authorization. The separate `ROBIN_BSK_APPLICATIONS_READY=1` gate requires a real read-back/receipt pilot; Phantom (`ndretlzi`) has now passed one on Ashby. Keep the daily limit small; `validateOnly` is permitted for diagnosis. The old `jobright-checked-v1` contract remains readable for historical records.
- The user confirmed a reusable answer: they do not know anyone who works at employers they apply to. `confirmedFacts` stores this; the reviewer supplies `No` only for a matching acquaintance question and exact available option, never for different referral/permission questions. A reviewer-proposed `Yes` for that question is rejected. Smartsheet's exact question also has a scoped approved `No` answer. The approved local PDF's exact bytes/hash are authoritative for auditing qualifications, not for selecting the uploaded file. The user explicitly delegates resume upload to Jobright: never replace its attachment or require its bytes/name to match the local PDF. Jobs notes and explicitly confirmed answers/facts supply preferences and user decisions; the old scoring CV and Jobright's profile are not candidate evidence.
- Approved answers are saved in `job-application-settings.json`, projected to the current job by `applicationAnswers()`, and included with confirmed facts in review evidence. For a blank field under the trusted Jobright policy, the reviewer now deterministically uses an exact saved question/answer or an unambiguous standing personal category when a unique form option matches; this also applies to optional fields the user explicitly filled in the profile. Populated Jobright answers stay untouched. Unknown categories, essay-like labels, pending dropdown selections and missing/ambiguous options still need review; another job's pay/legal approval never carries over. `2026-11-06` audit: all 11 standing categories, 17 general answers and 4 job-scoped answers are saved; the only current `attention` job asks about startup funding stages and an unrelated guacamole recipe, neither of which is a stored personal fact. - `lib/job-application-review.ts` uses a fresh, one-shot, **zero-tool** assistant turn. Employer text, questions, options and autofilled values are untrusted data. The model returns a bounded decision for every non-file field with exact source quotations; it cannot operate the browser or submit. Runner-supplied `workflow` provenance can answer discovery-source questions (including “How did you first learn about us?”), never candidate qualifications, personal referrals, prior employment or permissions.
- Check optional populated fields too. Clear unsupported demographic/consent defaults rather than silently accepting them or choosing “decline” for the user. Once the user fills the **reusable personal answers** profile, unambiguous variants of pronouns, race/ethnicity, sponsorship now/future, US work authorization, citizenship and other listed demographic categories can be answered from that standing approval. Do not infer future sponsorship from present need, Hispanic identity from race, or citizenship/unrestricted authorization from “no sponsorship”. Only the user's explicitly saved values, supported options and exact evidence quotes pass read-back. Unknown or mismatched options still need attention.
- Store a posting-specific pay or legal approval as `answers["[job:<id>] <exact question label>"]`. The runner projects only general answers that are neither pay nor legal choices, plus that job's overrides, before constructing model evidence and validating protected answers. Legacy generic pay/legal answers remain stored but no longer grant approval at another job. Salary expectations need the exact role question; agreements, attestations, background checks, arbitration and personal-completion declarations need the employer's exact question. Identical wording elsewhere is not authorization. Reservation/submission hashes still bind the full approved configuration.
- Jobs › Applications › **Settings & approved sources** › **Edit personal answers** is the user's private, once-filled editor. Settings are collapsed by default and the private answer API is not fetched until the editor opens; `/dashboard/jobs#application-answers` explicitly opens it for existing bookmarks. `/api/robin/jobs/applications/answers` GET returns only approved facts/answers (`no-store`); PATCH atomically saves the reusable profile (structured standing categories, other confirmed facts and recurring exact-label Q&A) with an expected revision to reject stale tabs, or edits one exact question on a recorded, unsubmitted job. It never changes the approved PDF, schedule, submission policy or job records, and cannot create generic salary/legal consent or invent a form option. The general application board remains redacted. Do not prefill personal examples from a conversation. Saving while checked auto-submit remains on displays explicit warning and acknowledgement; saving itself never runs or submits an application.
- The user delegates drafting and filling open-ended full-stack/project essays from the approved CV and confirmed facts without a separate question-tracking handoff. Treat these sources flexibly: synthesize and paraphrase facts, use product purpose for 'why', documented design choices for 'challenge', and grounded qualitative outcomes when no metrics exist; no saved question-specific answer, personal origin story or measured impact is required. Distinguish AI used *in the product* from unverified AI coding-assistant usage. The usual exact supporting source quote anchors the account and form read-back/submission gate still applies. Employer prose and old scoring CV cannot establish personal project facts. Invented metrics, hardships, employment, personal motives or AI-use anecdotes are not allowed. If a required claim genuinely has no source, request that specific fact rather than invent it or quietly submit an incomplete answer. No separate todo is created for answerable essays, but the application audit must still retain field/evidence decisions and the receipt boundary; 'don't record the question' does not authorize deleting the audit trail or hiding an unresolved legal/personal declaration.

## Seam and storage

- `extension/robin/job-application-domain.ts` owns configuration, PDF identity, selection, reservations, the durable submission gate and receipts. The runner/HTTP adapters do not import `store.ts`.
- `Job.application` uses the existing SQLite/JSON jobs collection: version, attempt id, reservation days, field evidence, autofill completion, source hashes, model decisions, stage, submission grant, bounded validation-rejection history and receipt. No new operational JSON store or database migration. Intake retains application evidence.
- The read-only application board projects away `description` and scoring `review` before SQLite deserialization, retaining every application record and daily attempt/receipt total. Six paired snapshot runs measured 95–97 → 39–44 ms with identical output. JSON/mixed storage still behaves correctly. These partial rows never enter persistence, candidate selection or submission checks.
- Known-ID readback, dismissal, preparation results, rejection/uncertainty updates and receipts use selected-row persistence, re-reading under the existing transaction. Reservations and submission grants deliberately keep full-collection reads: `preparableJob` must check other roles' duplicate locks. Never narrow those checks just to speed up a write.
- `job-application-settings.json` is configuration: schedule, PDF path/hash, confirmed answers/facts, preference hash and submission policy. The public API can edit the schedule, not inject answers, a PDF path, submission policy or receipt.
- Unknown personal facts/choices are `attention`; failed controls/read-back are `error`; a verified missing posting is `unavailable`. A user-reported manual Submit without a receipt is `uncertain`, blocks both automatic and explicit re-preparation even after approval-source changes, and never marks Applied. The 2026-11-03 SambaNova test (`jwh5vmst`) is in this state after the user reported clicking Submit; no Robin receipt was verified. Unavailable records remain visible and keep the user's pipeline status, do not retry just because approved facts change, and do not claim an unsubmitted role against a new requisition. Applied history and submission locks always retain duplicate protection.
- Every application record exposes its persisted `application.url` as an ordinary new-tab “Open application page” link, including failures, unsupported boards, uncertain outcomes and submitted history. This is manual navigation, independent of the Chrome worker and its busy state; render only HTTP(S) links and never treat opening one as a retry or submission. `resumeVerified: false` with no captured form fields is **not** proof the resume was absent: `JOBRIGHT_INCOMPLETE` stops after the Autofill click when the expected completion report was not observed, before the form/attachment read-back. The board says “not checked”; only a captured form with no attachment says “not observed.”
- “Remove record” (`dismiss`) persists `application.dismissedAt`: exclude it from board rows/counts and automatic selection, even after approved-source changes. Keep the Job, daily attempt/submission totals, receipts and submission/duplicate locks intact; late worker writes must not resurrect it. Explicit preparation can create a fresh visible attempt only through the unchanged safety gates. The UI confirms list-only removal and disables it during browser work; technical-failure labels, counts and blocker text use `--danger`, distinct from questions needing an answer.
- Workflow v2 distinguishes legacy preparation-only records. Those records remain visible as legacy and can be rerun; they are not counted as current-workflow attempts. Existing Applied/submission evidence always prevents reapplication.
- Approval hashes include the answer-reference PDF, Jobs-note hash, answers, standing personal answers (when present), confirmed facts, submission policy and browser-audit contract. A changed source invalidates an old review. Never silently advance the preference hash to bypass reconfirmation.

## Scheduling and ownership

`startApplicationScheduler()` starts in node instrumentation and refreshes after dev HMR on application GET. It checks each minute using IANA local time/DST. Defaults: off, 09:00 America/Los_Angeles, five roles per automatic run. The persisted `dailyLimit` key is legacy naming: it bounds each run (1–20), **not the whole day**. The default is five; this user's existing setting is 20. Zero pauses unattended runs; enabling from zero sets a five-role batch. A sleeping Mac processes current eligible roles, not missed previous days.

The existing `job-applications` background lease serializes browser operations across processes; commits use its ownership fence. Before a production preparation batch reserves its first job, `bsk status` verifies the configured Chrome instance is connected and responsive; missing CLI reports `BSK_CLI_MISSING` instead of one generic transport error per job. A manual start performs this read-only check before returning 202 so the user sees a synchronous failure; the worker rechecks after ownership to guard a disconnect race. Scheduled preflight failures are recorded as a bounded, sanitized `applicationPreflight` entry in the existing job-digest runtime document; the board shows the reason and timestamp without claiming a role attempt, and a successful preflight clears it. A later per-job disconnect still fails closed and consumes that attempt; this is a preflight, not a guarantee of browser availability throughout a run. Reservations count as attempts even on failure. The automatic scheduler checks each minute after the configured time and processes up to the configured number (maximum 20) of eligible roles per run, then continues on later checks without a daily ceiling. Selection excludes same-approval attempts, submitted/uncertain jobs and jobs still awaiting known answers; no repeated blind application. Candidate snapshots, per-role preparation/duplicate locks and submission/receipt gates remain intact. The workbench offers an enable/pause control rather than a manual continuation batch. Receipt-confirmed submissions are counted separately. A pause stops new reservations, not a browser operation already in flight.

Eligibility reuses digest freshness/title/experience/duplicate gates, but has a separate **3.5 exploratory application floor**; the verified recommendation/Push floor remains the profile's 3.75. This user explicitly permits submitting when JD qualifications cannot be verified, not inventing answers: require a current scored posting (`scoreContext` matches), reject known blocked checks/flags and suspect verification failures (except genuinely incomplete JD), and label missing JD as provisional rather than verified. Application geography is stricter than the legacy discovery profile: a named Bay Area city or Remote that can be worked from the Bay Area; `USA` alone and `Remote - New York City, NY` are not enough. This avoids a profile rewrite that would trigger hundreds of paid re-scores. Allows eligible shortlists and ignores notification status. Only supported direct Ashby/Greenhouse URLs (primary or stored alias, still subject to the browser's identity check) enter automatic selection; sorting unsupported links to the back still eventually wastes daily reservations. Explicit preparation refuses unsupported targets before reserving a day, without altering historical failures. Existing current-workflow records suppress automatic selection until their approved sources change; confirming all known missing answers makes a role eligible for a fresh audit on a later automatic run. Applied records, submission locks and same-company/title/requisition duplicates remain excluded regardless of source changes. Explicit technical reruns cannot bypass Applied, submission locks or duplicate protection. Account access and other ATS adapters are not solved by pretending unsupported pages were filled.

## Daily application report

The Jobs › Applications card now reads a bounded, read-only daily report above the existing history: attempted roles (distinct reservations, even on failure) and receipt-confirmed submissions are separate; unresolved personal questions and uncertain submissions are called out without triggering a retry. It includes today's records and previously unresolved attention/uncertain rows, at most 40 visible report rows; dismissed rows are not resurrected, but their attempts/receipts remain in the totals. The report's day follows the configured application timezone and labels its as-of time. Opening it never sends, audits or submits. A report row can open the already available application history record without loading approved answers. The UI leads with today's attempts versus receipt-confirmed submissions, shows today's outcomes separately from a collapsed earlier-unresolved list, and folds all-time status counts under application history; never display cumulative attention/uncertainty as today's outcomes.

The Web scheduler also runs one read-only daily pipeline check at/after 19:30 in the application timezone, independently of the optional push report. It snapshots discovery freshness/errors, scoring backlog/error, today's discovered/unscored jobs, currently eligible candidates, attempts versus receipts, unresolved submissions and bounded failure categories/job ids in `job-digest-state.json.applicationChecks` (14 days). The Jobs application desk displays the latest check. Unknown technical causes are labelled `UNCLASSIFIED_ERROR`, never treated as successful or guessed; the original blocker stays on the Job application record for investigation. It does not scan, score, click, retry, or backfill a sleeping Mac's missed days. Browser/network failure and an empty eligible supply are warnings, not reasons to weaken eligibility, receipt or duplicate gates. Daily output is only guaranteed while the Web scheduler is running; it cannot guarantee an employer posts a suitable job or accepts a submission.

A separate default-off `ROBIN_JOB_APPLICATION_REPORT_ENABLED=1` enables one phone-only evening report from the existing Web application scheduler at/after 18:30 in the configured timezone **only when the application schedule is enabled**. It checks the configured push channel and a subscription, freezes the report in the already registered `job-digest-state.json` (additive `applicationReports` field, not a new v3 operational filename), claims before network, and uses a stable day/timezone notification identity. One acceptance counts as push-service acceptance, not physical display. An ambiguous, timed-out or abandoned send is never automatically retried; a definite nonacceptance is marked failed. A late wake reports the current day only; unresolved candidates delay a zero-attempt snapshot until 19:30, after which the message says candidates remain. The notification contains counts only, no form answers, resume data, blocker text or source evidence. A subsequent run/receipt changes live application records but never rewrites or resends that day's frozen report. Each completed production preparation run with at least one processed role also claims an independent, once-per-run Push summary (counts only), without requiring the evening-report environment switch. Both ledgers are inside the registered job-digest state. An uncertain Push send is never replayed. Neither run summaries nor the optional evening report send while the application schedule is disabled.

## Submission and receipt boundary

`grantApplicationSubmission()` rechecks live authorization, answer-reference PDF/preferences, attempt ownership/source hash, Autofill completion, resume attachment presence, every required field, complete decisions and no unresolved issues. It **atomically persists `submitting` and a short-lived, snapshot-bound nonce before any click**.

The browser verifies the grant fingerprint, expiry, same posting and fresh field values, then performs exactly one Submit activation. A browser session marker also prevents repeating that attempt. Any uncertain outcome remains locked against automatic retry, including after process/lease loss; no preparation write can erase a persisted submission boundary. The board projects an interrupted submitting row as uncertain, not retryable.

The Web scheduler also checks pending, durably granted Greenhouse attempts against read-only Gmail every five minutes (including while new submissions are paused). Only an exact Greenhouse sender, explicit employer confirmation phrase, exact company in the subject, arrival after the grant within 24 hours, and exactly one pending submission for that employer may settle the same Robin job id. Duplicate or incomplete mail, multiple candidate messages, an employer without a grant, and Ashby mail without a verified sender/format leave the record uncertain. Gmail failure never releases a submission lock. Mail receipt provenance stores `source=email` and `mailId`; the saved posting URL is the Robin association, not a claim that the email named a requisition.

An explicit Ashby “Your form needs corrections” heading plus “Missing entry for required field: …” and the still-visible form is a **definitive validation rejection**, not uncertainty. `confirmApplicationRejection()` checks posting/attempt/time, archives that evidence and releases the lock without marking Applied. The runner permits only one automatic recovery: a fresh attempt, Jobright run, full audit/repair and new grant. Repeated rejection stops as an error. Generic errors, timeouts and absent receipts do not release the lock.

A success heading, explicit confirmation prose, absence of the visible form and the same marked posting are required for a receipt. Greenhouse's exact `/company/jobs/id/confirmation` path is the same requisition for receipt inspection only, not a new application target; record the actual confirmation URL. Recovery from an earlier uncertain record uses receipt inspection, never another Submit. The domain rechecks identity and atomically records Applied plus receipt. `receipt` is inspection only; no public endpoint accepts receipt text or offers a bypass Submit action. Other redirected/ambiguous success pages and server validation failures are not successful submissions and do not justify blind retries. User-controlled manual Applied remains separate.

## Board list disclosure

The Jobs results column leads with a compact **Auto-apply** desk above Discoveries and OAs/interviews. It shows one primary auto-apply enable/pause action, receipt-confirmed submissions (not attempts), today's attempts and the per-run batch size; no daily-quota progress bar, five-tile dashboard or default-open attempt log. Current questions are the first action-oriented section, with an inline, focused exact-option answer editor that fetches private answers only when opened; the full reusable profile and PDF explanation remain in collapsed settings. Technical/uncertain follow-up and application history are separate disclosures; the detailed audit, daily report rows, filters and all-time counts are inside history. The header jump links follow this order. Opening records from the report expands history without changing application state.

The application desk keeps a **Needs your input** list of current-workflow `attention` records above the history disclosure, open on arrival when answers are needed. Its separate follow-up list is now open by default, with uncertain submissions first and each role's next step, receipt check and direct confirmation-mail search visible. Unresolved current-workflow rows (questions, errors, unavailable postings and uncertain submissions) are never aged out by the 100-record history window; only resolved history is bounded. A user approval alone cannot release an uncertain Submit lock: first obtain an attributable receipt or definite proof the employer did not receive that application, then re-audit before any reapplication. The current product has no evidence-backed reapply approval endpoint; do not present a follow-up control as one. Each unsubmitted `attention`/`blocked` application may also be explicitly **Dropped** from the question list: a confirmed user action atomically marks that Job `dropped` and its application record dismissed, while preserving attempt/evidence/receipt history. This declines the whole role, never skips a required question; submission-locked and receipt-confirmed roles cannot use this action. The client refreshes the Jobs list immediately after the server acknowledges the drop. It shows only required or populated non-file fields that failed approval (or recorded blockers when no form was captured), plus an explicit route to the private exact-question editor. When approving one field changes the global approval hash, the old read-back remains `blocked` as historical evidence, but the board derives pending question keys from the current job-scoped/exact-match answers and the reviewer's unambiguous standing-answer mapping (including supported choices), keeping the *other* questions visible without exposing answer values. Technical `error`, `unavailable`, `uncertain` and successful receipts are not presented as personal questions. Opening this list or its `/dashboard/jobs#application-questions` deep link never fetches private approved answers or changes applications; a hard question stays in its own record while the runner continues with other eligible roles. Each unresolved captured question opens a compact editor beside that question, preselected to that job and exact field; it fetches private answers only then. A non-pay/non-legal question can optionally be approved for future exact-question matches through the existing reusable profile; job-specific pay/legal choices cannot. A conflicting saved job override must be removed before a different reusable answer can be used. Saving an approved answer never triggers a browser action; the focused editor advances to the next unresolved question. Only after all known questions are answered may the next enabled automatic run re-audit and potentially submit through the normal duplicate/receipt/submission gates. Technical failures, unavailable postings and uncertain submissions live in a separate follow-up list with reason and next step; uncertain submissions offer receipt inspection, never a rerun. Retryable technical failures require a deliberate rerun after repair. The report displays live counts and outcomes even after the evening Push snapshot is frozen: only its delivery status remains from that snapshot.

The historical BSK successes, failures, unknowns and confirmed fixes are summarized in the personal `~/.pi/agent/skills/job-application-bsk/` skill, as a field guide rather than permission to weaken the current safety contract.

Within the collapsed history disclosure, the filtered automation list initially shows at most five records. Longer lists have a keyboard-accessible “Show all N records” / “Collapse list” button; changing the status filter resets the list to five. The auto-apply control, receipt-confirmed count, today's attempts and current questions remain visible above history. Disclosure changes are presentation state only, never dismissal or a workflow mutation. `e2e/jobs-board.mjs` covers the five/six-row boundary, expand/collapse, keyboard focus and empty/short filters in both languages.

## Browser polling

The applications board reads immediately on mount/visibility return or explicit
action completion. It polls every 5 seconds while the server reports `running`,
and once a minute at rest; hidden documents stop automatic intervals. Only the
browser read cadence changes—no scheduling, authorization or submission behavior.
`e2e/background-polling.mjs` mocks all reads and forbids mutation requests.
