# Jobs application automation

The user-approved workflow is **Jobright Autofill → audit against approved sources → repair → submit if all checks pass → confirm receipt**. Jobright is the initial filler, not a source of truth. Routine omissions are the worker's job, not a mandatory manual-review handoff. Attention is for genuinely unknown personal facts, permissions or account access; technical failures have a separate status. Never call an attempt a successful application.

## Authorization and trust

- Default scheduling and automatic submission are off. `submissionPolicy: "jobright-checked-v1"` records explicit user authorization for checked submission. Enabling the schedule alone does not grant that authorization. This is a scoped Robin workflow, not a blanket change to Career-Ops' manual-application defaults.
- The approved local PDF's exact bytes/hash are authoritative for auditing qualifications, not for selecting the uploaded file. The user explicitly delegates resume upload to Jobright: never replace its attachment or require its bytes/name to match the local PDF. Jobs notes and explicitly confirmed answers/facts supply preferences and user decisions; the old scoring CV and Jobright's profile are not candidate evidence.
- `lib/job-application-review.ts` uses a fresh, one-shot, **zero-tool** assistant turn. Employer text, questions, options and autofilled values are untrusted data. The model returns a bounded decision for every non-file field with exact source quotations; it cannot operate the browser or submit. Runner-supplied `workflow` provenance can answer discovery-source questions (including “How did you first learn about us?”), never candidate qualifications, personal referrals, prior employment or permissions.
- Check optional populated fields too. Clear unsupported demographic/consent defaults rather than silently accepting them or choosing “decline” for the user. New agreements, attestations, citizenship/demographic answers and background-check permissions require explicit question-specific approval. Do not infer unrestricted authorization merely from “no sponsorship”.
- Store a posting-specific approval as `answers["[job:<id>] <exact question label>"]`. The runner projects only general answers and that job's overrides before constructing model evidence and validating protected answers; an identical consent question at another employer is not authorized. Reservation/submission hashes still bind the full approved configuration.
- CV-grounded project prose is allowed when authorized. Invented metrics, hardships, employment, personal motives or AI-use anecdotes are not. Required missing facts become specific questions, not “review the entire form”.

## Seam and storage

- `extension/robin/job-application-domain.ts` owns configuration, PDF identity, selection, reservations, the durable submission gate and receipts. The runner/HTTP adapters do not import `store.ts`.
- `Job.application` uses the existing SQLite/JSON jobs collection: version, attempt id, reservation days, field evidence, autofill completion, source hashes, model decisions, stage, submission grant, bounded validation-rejection history and receipt. No new operational JSON store or database migration. Intake retains application evidence.
- `job-application-settings.json` is configuration: schedule, PDF path/hash, confirmed answers/facts, preference hash and submission policy. The public API can edit the schedule, not inject answers, a PDF path, submission policy or receipt.
- Unknown personal facts/choices are `attention`; failed controls/read-back are `error`; a verified missing posting is `unavailable`. Unavailable records remain visible and keep the user's pipeline status, do not retry just because approved facts change, and do not claim an unsubmitted role against a new requisition. Applied history and submission locks always retain duplicate protection.
- Every application record exposes its persisted `application.url` as an ordinary new-tab “Open application page” link, including failures, unsupported boards, uncertain outcomes and submitted history. This is manual navigation, independent of the Chrome worker and its busy state; render only HTTP(S) links and never treat opening one as a retry or submission.
- “Remove record” (`dismiss`) persists `application.dismissedAt`: exclude it from board rows/counts and automatic selection, even after approved-source changes. Keep the Job, daily attempt/submission totals, receipts and submission/duplicate locks intact; late worker writes must not resurrect it. Explicit preparation can create a fresh visible attempt only through the unchanged safety gates. The UI confirms list-only removal and disables it during browser work; technical-failure labels, counts and blocker text use `--danger`, distinct from questions needing an answer.
- Workflow v2 distinguishes legacy preparation-only records. Those records remain visible as legacy and can be rerun; they are not counted as current-workflow attempts. Existing Applied/submission evidence always prevents reapplication.
- Approval hashes include the answer-reference PDF, Jobs-note hash, answers, confirmed facts, submission policy and browser-audit contract. A changed source invalidates an old review. Never silently advance the preference hash to bypass reconfirmation.

## Scheduling and ownership

`startApplicationScheduler()` starts in node instrumentation and refreshes after dev HMR on application GET. It checks each minute using IANA local time/DST. Defaults: off, 09:00 America/Los_Angeles, five distinct attempts; the user's live configured limit is ten. A sleeping Mac catches up on the current local day, not missed previous days.

The existing `job-applications` background lease serializes browser operations across processes; commits use its ownership fence. Reservations count as attempts even on failure, preventing an infinite same-day failure loop. Receipt-confirmed submissions are counted separately. A pause stops new reservations, not a browser operation already in flight.

Eligibility reuses digest score/evidence/freshness/target gates, allows eligible shortlists, and ignores notification status. Supported direct Ashby/Greenhouse URLs come first. Existing current-workflow records suppress automatic selection until their approved sources change; confirming a missing answer makes them eligible for a fresh audit when daily budget remains. Applied records, submission locks and same-company/title/requisition duplicates remain excluded regardless of source changes. Explicit reruns cannot bypass Applied, submission locks or the distinct-job daily limit. Account access and other ATS adapters are not solved by pretending unsupported pages were filled.

## Browser boundary

- `scripts/job-application-page.mjs` is a self-contained function executed in Playwright CLI's restricted VM: no Node `URL`, `Buffer` or timers. Browser-side `evaluate()` has browser APIs. Keep the VM fixture test.
- Only uncredentialed HTTPS URLs on supported ATS hosts enter the worker. Verify the exact requisition, role and employer before autofilling. Roman/numeric seniority normalization is identity matching, not qualification inference. An aggregator's trailing season/year can be absent from the employer's title only when the remaining core matches exactly on the same requisition; conflicting years and seniority still fail. A missing-posting heading gets `POSTING_UNAVAILABLE`, not a generic title/control failure, and is not retried as a transient autofill error. Tenant/logo identity evidence avoids requiring a company's name in only the visible body.
- Probe the named CLI session before attaching. Repeated `attach` replaces its tracked context and loses drafts. Only inspect matching posting URLs before reading `window.name`; discarded/extension tabs can hang.
- Invoke the actual Jobright shadow-DOM Autofill control. Observe a busy state followed by the completion report, not merely a button click or “100%”. Jobright can reload the same posting with `jr_id`; tolerate that transition. A paused Skip control skips only Jobright's stalled step, never the employer's required question. Our audit must still resolve it. A timed-out second wait continues the same autofill rather than restarting it. Periodically request an in-memory paint while waiting: Jobright's own work can stall in an occluded tab and finish long after the worker timeout.
- Chrome's extension bridge can report a tab hidden with zero animation frames even after `bringToFront`. Use a checked native activation of the actual DOM control rather than depending on Playwright's two-frame click stability wait. This is not a private Jobright/ATS API. Non-submit activations temporarily suppress default form submission (Ashby choice buttons may omit `type=button`). Only the final gated activation permits a submit event.
- Common repair adapters cover ordinary inputs, native selects, exact combobox options and choice groups. Ashby marks required labels by CSS class; its hidden checkbox mirrors must not become extra answers/options. Recommit approved choices through their handlers: a checked DOM value alone may not have reached Ashby's server (Quora Degree and Brainco US-authorization failures). Ashby's radio fieldset can be nested inside the element owning `data-field-path`: resolve the ancestor, not just the fieldset's own attribute. Its custom radio permits deselect/reselect through clicks; await each save before reading checked state. Do not select an opposite answer or invoke private React/ATS methods to force a save. For Ashby field changes, wait for that field path's `ApiSetFormValue` response after each committed change, including text clearing and clearing/reselecting an already checked option. Otherwise the next field's whole-form response can restore an unsupported old answer (observed with Sierra's optional junk-food answer). Check HTTP and GraphQL success; a failed acknowledgement is a submission blocker even when the DOM looks correct. Toggling twice before the first save settles can leave the backend empty. An in-memory page capture requests the paint needed by deferred effects; no image is stored. Do not depend solely on `document.hidden` or an immediately read `aria-expanded`: they can describe the preceding render.
- Jobright owns resume selection/upload. The browser receives no local PDF bytes and has no resume replacement path. Check only attachment presence: a resume input's file list or a visible attachment filename within the resume section. Greenhouse can remove its input and use a `div.upload-label` inside `.file-upload`; do not require a Replace control. Record a synthetic file field for a rendered attachment when the input is gone, so read-back still binds its filename. Never use a cover letter, accepted-format hint or Jobright's own panel as resume proof. The persisted `resumeVerified` field now means attachment presence, not byte identity; older records had stricter hash checks. Additional unapproved attachments are not accepted.
- Combobox repair types the query, presses ArrowDown (native `click()` does not open React Select), paints, then selects a unique exact option from that input's list. Never use an unrelated global listbox (Quora has a date calendar and school picker). Ashby's school options have a canonical name plus country/domain; choose the canonical label, not concatenated text or an invented campus option. A shorter school search only reveals options for a fresh audit, never authorizes a guessed school. `pendingSelection` blocks submission even if the search text matches the desired answer.
- Phone number and embedded SMS consent are separate fields; a required phone must not make optional texting consent mandatory. A preselected ordinary native radio has no unset action (`canClear: false`); Ashby's custom `.ashby-application-form-input-radio-group` does support deselection and optional unknown answers there can be cleared. For ordinary radio groups, unsupported consent there needs the user's explicit choice, not endless clearing attempts or an invented default refusal. The datepicker's month announcement is not a validation error; real error alerts remain blockers. Dropdown menu options are not extra form fields.
- Up to three audits handle changed/conditional fields and newly revealed combobox options; clearing a demographic parent can remove its dependent question. Final live read-back must match every planned answer, with no pending dropdown selection. File-list/DOM evidence is not proof of ATS server persistence.
- Payloads live in a private directory and are removed in `finally`. Never expose raw CLI output, extension tokens or connection URLs. Children receive an environment allow-list, not Robin/provider credentials. Error diagnostics expose only controlled codes/error types, not raw transport output.

## Submission and receipt boundary

`grantApplicationSubmission()` rechecks live authorization, answer-reference PDF/preferences, attempt ownership/source hash, Autofill completion, resume attachment presence, every required field, complete decisions and no unresolved issues. It **atomically persists `submitting` and a short-lived, snapshot-bound nonce before any click**.

The browser verifies the grant fingerprint, expiry, same posting and fresh field values, then performs exactly one Submit activation. A browser session marker also prevents repeating that attempt. Any uncertain outcome remains locked against automatic retry, including after process/lease loss; no preparation write can erase a persisted submission boundary. The board projects an interrupted submitting row as uncertain, not retryable.

An explicit Ashby “Your form needs corrections” heading plus “Missing entry for required field: …” and the still-visible form is a **definitive validation rejection**, not uncertainty. `confirmApplicationRejection()` checks posting/attempt/time, archives that evidence and releases the lock without marking Applied. The runner permits only one automatic recovery: a fresh attempt, Jobright run, full audit/repair and new grant. Repeated rejection stops as an error. Generic errors, timeouts and absent receipts do not release the lock.

A success heading, explicit confirmation prose, absence of the visible form and the same marked posting are required for a receipt. Greenhouse's exact `/company/jobs/id/confirmation` path is the same requisition for receipt inspection only, not a new application target; record the actual confirmation URL. Recovery from an earlier uncertain record uses receipt inspection, never another Submit. The domain rechecks identity and atomically records Applied plus receipt. `receipt` is inspection only; no public endpoint accepts receipt text or offers a bypass Submit action. Other redirected/ambiguous success pages and server validation failures are not successful submissions and do not justify blind retries. User-controlled manual Applied remains separate.

## Board list disclosure

The filtered automation list initially shows at most five records. Longer lists
have a keyboard-accessible “Show all N records” / “Collapse list” button; changing
the status filter resets the list to five. Counters, warnings and workflow controls
stay visible. This is local presentation state only, never dismissal or a workflow
mutation. `e2e/jobs-board.mjs` covers the five/six-row boundary, expand/collapse,
keyboard focus and empty/short filters in both languages.

## Browser polling

The applications board reads immediately on mount/visibility return or explicit
action completion. It polls every 5 seconds while the server reports `running`,
and once a minute at rest; hidden documents stop automatic intervals. Only the
browser read cadence changes—no scheduling, authorization or submission behavior.
`e2e/background-polling.mjs` mocks all reads and forbids mutation requests.

## Validation

- `node --test extension/robin/job-application-domain.test.mjs lib/job-application-review.test.mjs lib/job-application-runner.test.mjs app/api/robin/jobs/applications/route.test.mjs`
- Repeat with `ROBIN_TEST_TASK_BACKEND=json`.
- `node --test e2e/job-applications.mjs`: isolated local Chrome/CLI-VM fixture, simulated Jobright, repairs, unsupported defaults, occluded renderer, single submit, changed/expired grants and duplicate refusal. Never a real employer.
- `PLAYWRIGHT_CHANNEL=chrome node --env-file-if-exists=.env.local e2e/jobs-board.mjs`: mocked dashboard data, bilingual statuses, honest counters, existing Jobs behavior, light/dark and mobile widths. Reuse the healthy dev server; never build during dev.
- Fixture success is **not** real-application acceptance. Keep scheduling paused during migration and validate real forms/receipts before claiming unattended daily operation works. Never reapply to an already submitted role for testing.
