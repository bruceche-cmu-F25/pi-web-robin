# Mobile and browser behavior

## Shared touch styles (`app/globals.css`)
- Shared `.ui-action` and Robin navigation hover styles run only under `(hover: hover) and (pointer: fine)`. Do not restore the `(hover: none)` reset table: it loses to variant specificity (notably destructive chips). Press feedback wins over variant hover fills; disabled/inert controls remain excluded.
- Fields stay at least 16px under `(max-width: 640px), (any-pointer: coarse)`, covering landscape phones and touch tablets with a paired mouse. Larger fields declare `--field-font-size` on the field itself and use it in their base font; the shared `max(16px, var(--field-font-size, 16px))` floor must not shrink titles/goals. No local `!important` font workaround; chat preserves larger user font sizes. Do not disable viewport zoom. `text-size-adjust: 100%` prevents landscape font inflation.
- Controls use `touch-action: manipulation` and non-selectable labels at low specificity, so dedicated drag surfaces can override them. Tap highlights are suppressed only on shared controls with explicit press feedback. Prose and ordinary links retain selection and native callouts.
- The narrow Robin drawer scrolls as a whole, with `overscroll-behavior-y: contain` and non-shrinking direct children, so short landscape screens retain 44px entries and reachable bottom utilities.
- Regression: `PLAYWRIGHT_CHANNEL=chrome node --env-file-if-exists=.env.local e2e/mobile-native.mjs` mocks application APIs and checks touch/mouse CSS, press feedback, fields and navigation at 320–1024px. `E2E_GLOBAL_CSS` optionally supplies PostCSS-built current `app/globals.css` when the shared dev watcher is stale (replaces that sheet, not an override). This is a browser layout check, not hardware verification of iOS zoom, keyboard, safe areas or touch feel.

## Typography
- Follow [Typography](../typography.md). `app/globals.css` owns `--type-page-size` (32px / below 960px 24px), `--type-section-size` and `--type-action-size`. Page titles use `.pi-page-title` or the same token in their CSS module; never blanket-target `h1`, change the 13px root, or apply the workspace title scale to document headings, settings, code or charts.
- Robin small-copy leading defaults to unitless 1.6 at zero specificity; preserve Tailwind `--tw-leading` and explicit local reading/control leading. Mobile does not re-override it. Notes/Obsidian phone actions and FSO controls use readable 13px UI type with 44px targets; dense graph labels are a different role.
- `e2e/typography.mjs` uses mocked APIs, checks the title/field/leading contracts and captures 104 states. Its `E2E_GLOBAL_CSS` source-built fallback has the same limitation as mobile-native: passing against replacement CSS does not prove the running dev server has refreshed its cache. Real iOS typography/keyboard behavior remains a hardware check.

## Mobile software keyboard (`hooks/useViewportHeight.ts`)
- While an editor has focus and the visual viewport is more than `KEYBOARD_MIN_HEIGHT_PX` (60px) shorter than `innerHeight / scale`, the hook writes `visualViewport.height` to `--app-viewport-height`; smaller shrinks are Safari toolbars. Always compare against that zoom-corrected height, or iOS auto-zoom and pinch zoom leave the composer behind the keyboard.
- WebKit settles the shrunken height only after the keyboard animation, often without another `resize` (bugs.webkit.org 265578), and an IME candidate bar resizes the keyboard with no viewport event at all. So every trigger, composition/input/keyup events on a focused editor included, starts one non-restarting chain of re-reads (`SETTLE_DELAYS_MS`). Reading once per event keeps the full-screen height, and `scrollTo(0, 0)` then fights the page scrolling to the caret: a jittering composer.
- The same check sets `<html data-keyboard-open>`. Under `(max-width: 640px), (pointer: coarse) and (max-height: 500px)` (phone landscape included; tablets keep their controls) CSS hides `.chat-input-controls`, `.extension-status-shelf` and a fresh composer's project bar (`.new-session-context`, its own rule: tapping it would close the keyboard anyway) and drops the bottom safe-area padding the keyboard covers. `MobilePwaLayout.test.mjs` asserts each targeted class exists on its component, so a rename cannot leave a rule silently dead.
- Anything fixed to the bottom of a phone screen sits inside `--app-viewport-height`, never at `bottom: 0`: iOS keeps the layout viewport, and with it `bottom: 0`, under the keyboard. The drawer and the right panel use `top: 0` with that height; the sidebar's bottom sheet (`.sidebar-sheet-layer` in `app/sidebar-menu.css`) is a layer of that height with the sheet at its bottom, and drops its safe-area padding under `html[data-keyboard-open]`.

## Terminal extra keys (`components/TerminalExtraKeys.tsx`, `lib/terminal-extra-keys.ts`)
- A touch device held in portrait gets Termux's two key rows under the terminal (`ESC / - HOME ↑ END PGUP`, `TAB CTRL ALT ← ↓ → PGDN`). Portrait comes from `screen.orientation` (then `window.orientation`), never from the viewport: the soft keyboard makes the viewport wider than tall, and the keys must stay while it is open. Left and right are Noto Sans Mono's `↓` and `↑` rotated 90deg: its latin subset has `↑`/`↓` but no `←`/`→`, which would fall back to a heavier system font.
- The keys are the panel's last grid row, so xterm's `ResizeObserver` refits above them instead of being covered. Buttons call `preventDefault()` on pointer and mouse down so the hidden xterm textarea keeps focus and the keyboard stays up.
- Keys go through `terminal.input(sequence, true)`, the same `onData` path (and the same connected / disableStdin checks) as typing. Arrows and Home/End follow xterm's application cursor mode; CTRL and ALT are one-shot and also modify the next character typed on the soft keyboard (`applyTerminalModifiers` in `onData`).

## Terminal theme (`lib/terminal-theme.ts`, `hooks/useTerminalTheme.ts`)
- The terminal header's sun/moon button switches the terminal alone between dark (the default) and light, apart from the app theme. The choice is per browser in `localStorage` (`pi-web:terminal-theme`), shared by every open terminal and synced across tabs by the `storage` event.
- A switch sets `terminal.options.theme` on the live xterm, never recreating it, so the shell and its SSE stream stay. The panel's chrome reads `--terminal-*` variables that `.terminal-panel[data-terminal-theme="light"]` overrides; `--terminal-bg` must match each xterm palette's `background`.
- Glass styles only the terminal's frame/header and the right panel's tab strip: local header ink/button tokens follow the app, but xterm's opaque background, ANSI colors, extra keys and independent light/dark preference remain the terminal's. The 8px frame inset and 44px header trigger the existing ResizeObserver fit, never a new terminal. Hidden right panels release decorative filters, not terminals; `e2e/glass-session-surfaces.mjs` checks both palette backgrounds and unchanged stream count through theme changes and hide/reopen with mocked terminal APIs (no real PTY is launched).

## Background push (`components/PwaRegistration.tsx`, `lib/push-client.ts`, `public/sw.js`)
- Register the same root service worker in both modes. Development adds `pushOnly=1`: no precache or fetch interception; activation removes only `pi-web-*` caches. Do not unregister it in dev: that disables push (and can discard subscriptions), while an unbounded `serviceWorker.ready` leaves Settings stuck on “Registering”. Production keeps its offline/cache behavior.
- Settings calls `registerPushNotifications()` directly from the click; permission must be requested before yielding the user gesture. Permission and subscription waits each have a 30 s ceiling, including non-abortable browser promises and response bodies. Timeout aborts fetch and fences late continuations; failed attempts release the shared in-flight slot so retry works. Background `setupPushSubscription()` never prompts or rejects. Keep the localized timeout message in Settings.

- Scheduled Robin notifications reuse `lib/web-push.ts` through authenticated `/api/push/send`, with bounded payloads, local links, per-occurrence receipts and explicit delivery counts (acceptance is not display). The existing bridge owns independent digest/reminder timer lanes; never also start them in Pi Web. Settings only chooses the delivery channel, leaving schedule enables/times and Telegram chat intact. See [Robin notifications](../robin-notifications.md) for scope, the reserved ledger recipient `0`, channel-switch replay prevention and failure limits.

## Completion sound
- `hooks/useAudio.ts` stores the toggle in `localStorage` as `pi-sound-enabled` and reuses one `AudioContext`.
- Autoplay policy requires unlocking sound from a user gesture: `ChatInput` calls the unlock hook from interactive controls, and `ChatWindow` plays the tone from `onAgentEnd`.
- A running context keeps an audio output stream open even when silent (an Android `AudioMix` wake lock, #1157), so it runs only around a chime or an unlock: `AUDIO_IDLE_SUSPEND_MS` after the last `resume()` settled it is suspended, unless a newer one is still outstanding, and turning sound off suspends at once. An unlock resumes a suspended context from the send's gesture (about 1 s of output stream per send), which lets later chimes resume it without one (Chrome and Firefox check the page's sticky activation; WebKit lifts its gesture restriction for good once that context started in a gesture). It is never closed: a new context made outside a gesture would stay silent on Safari.
- Firefox for Android leaves the `resume()` of a suspended context pending while the phone is locked, so a run's chime never played there (device report on #1178). `ChatWindow` therefore holds the context running while its session's `agentRunning` is true (`holdAudio()`, released when the run ends or the window unmounts): the output stream stays open during a run, not between runs. Chimes for sessions in other workspaces come from the sidebar's running poll, which stops while the page is hidden, so they never needed a hold. A chime whose `resume()` took longer than `AUDIO_STALE_CHIME_MS` (3 s) is dropped instead of playing when the user is back, including one requested before the page's first gesture.
- A stopped run is not a finished one (pi 1.1's `agent_settled.aborted`, which pi's own status reporting reads as idle, not done): `onAgentEnd({ aborted })` plays no tone and AppShell shows no browser notification, and the wrapper sends no "Task finished" push (`lastRunAborted`). The wrapper's `prompt_done` carries `aborted: true` for it, since the client finishes a prompt it sent on `prompt_done`, not `agent_settled`.
