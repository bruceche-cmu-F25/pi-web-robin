# Settings panels: plugins, skills and shared blocks

## General appearance
- Theme registration remains in `lib/theme.ts`; both settings surfaces use `ThemePicker` and first-paint restoration uses the same catalog. System/default now resolves to Glass (`glass`, light scheme) or Dark glass (`glass-dark`, dark scheme), using `SYSTEM_THEMES` in both first-paint script and the live hook. The paired material swatches come immediately after System. Explicit stored palette choices (including legacy Light/Dark) remain unchanged; missing, invalid or blocked storage follows the system. Its scoped palette/material CSS lives in `app/glass-theme.css`, imported after the base styles. Keep normal content colors opaque, blur only structural chrome, and use solid defaults before the filter-support query. Reduced transparency, more contrast and forced colors disable the material and decorative canvas. The approved standalone study (`public/prototypes/glass/`) now supplies the material language: detached 8–12px gutters, 38px control capsules, 30px sidebar/dialog corners, a pointer-transparent **1px** directional edge and light inset highlights, without the former 3px white rim or extra white sheen. **Clear** (30% tint, 0.7px softness) belongs to search/composer inputs, short toolbars, horizontal navigation and the mobile trigger; **frost** (48% tint, 10px blur) belongs to vertical navigation, sidebars and dialogs. Their semantic CSS `--glass-material` drives the renderer: a tall composer remains clear, not automatically frosted. Keep opaque content palettes and reuse the existing 4px/20px engineering grid from `globals.css` on the page, Glass shells and `.pi-grid-surface`; do not create a separate Glass grid. The study's photograph is not an app wallpaper. Overlays crossing arbitrary images/editors use 56% fill and stronger local ink (AA checked even over black). Light's 12% scrim avoids muddy grey glass, including Settings stacked above a phone sidebar. Embedded config surfaces are transparent and inner config sidebars use a 12% wash with no second blur; all these materials have opaque preference fallbacks. Both CSS materials work as the fallback; Chromium enhances them with a real SVG backdrop displacement map, not just a bright border. Keep the Dashboard header host transparent: its search capsule is the material. Chat's `.chat-input-surface:not(.is-compact)` is the material frame; quote editors stay unchanged. The ⌘K/Ctrl+K palette's native `.robin-command-dialog` is itself a frosted overlay (56% fill, stronger ink, 30px corner, 12% scrim). Its content wrapper and AssistantBar stay transparent, without a nested blur or shadow. Register the top-layer dialog with the lens controller, not the inner card, so it can sample the page behind it; closing releases its map. `e2e/glass-theme.mjs` checks both shortcuts, focus return, inner transparency, preference fallbacks and a rendered two-colour blur boundary in the native top layer. Never blur an inner sidebar again. The desktop chat sidebar (>640px) keeps a 12px left outer gutter in both Glass palettes, beside either the window edge or the navigation rail; its right/top/bottom spacing and internal tree alignment are unchanged. Closed sidebars have no gutter, and phone drawers retain their 8px offset. Mobile drawer offsets must be included in off-screen transforms; the existing gesture hook already includes computed left in its projection width. `e2e/glass-theme.mjs` checks selection, drafts, keyboard, reload, both top navigation modes, mobile/short-screen layout, composite contrast and preference fallbacks without real API writes. Its rendered two-colour backdrop probe also checks that colour actually transmits through the input centre and that the clear material keeps backdrop detail; computed `backdrop-filter` alone cannot prove this. It visits Models to catch opaque embedded sheets; run `e2e/navigation-gesture.mjs` with `E2E_THEME=glass` for touch settling and focus.
- Global navigation defaults to a **48px left icon rail** on desktop (≥960px). Chat's General › Appearance and Robin's Settings › Appearance both render `NavigationPlacementSetting`, backed by `hooks/useNavigationPlacement.ts` (`pi-web:navigation-placement`, `left | left-labels | top | top-icons`, default/invalid → `left`). The setting applies immediately, survives reloads, and follows other tabs; blocked storage keeps a page-local choice. Both `AppShell` and `RobinShell` change only their flex direction and navigation presentation, never remounting the workspace. Top restores the original masthead; “Top, icons only” keeps its position but hides names visually (not from assistive technology), with 44px targets, retained badges and hover/focus names below the bar. Narrow Robin pages retain their drawer; narrow Chat uses named Home / Chat / Notes / Learning / Incoming / Jobs / Research / More shortcuts regardless of desktop choice. `RobinMargin.module.css` owns their single-row layout: native horizontal scrolling (including focus reveal), no wrapping or shrinking touch targets, and badges on the actual destination rather than duplicated on More. More opens the existing Dashboard directory with session/cwd intact; no second drawer or menu state is introduced. The optional **184px left rail with labels** (`left-labels`) can also be toggled in the rail itself; it uses UI type and keeps badges visible. The default remains icon-only. No logo, new grouping or workspace remount. The rail keeps existing links, order, badges and theme tokens, with ≥44px targets, a scrollable primary list, fixed utility entries and hover/focus labels portaled outside the scroller. The standalone focus timer has been removed from all navigation layouts; the work queue's timer is unchanged. `e2e/navigation-placement.mjs` checks both settings, persistence/cross-tab sync, preserved chat DOM/styles/drafts, short-height scrolling, absence of the standalone focus timer and mobile navigation with mocked application APIs.
- Glass rail insets must exclude `.is-rail` from `.is-horizontal`: the rail carries **both** classes. The horizontal 12px inset squeezed a 48px rail's scrollport to 22px, clipping glyphs although its outer width and 44px buttons still passed size checks. Keep the base 1px icon / 6px labelled rail insets. Navigation focus reveals the whole entry with nearest scrolling before positioning its hint: Chromium can otherwise leave a partly visible link focused outside a narrow horizontal strip. `e2e/glass-left-surfaces.mjs` checks glyph clipping against ancestors and actual hit targets, Tab order, all four placements, 640/641 and 959/960 breakpoints, short screens, 180px sidebar controls, long multilingual session/project/file names, row/project menus, file scrolling, collapse/reopen, settings access and draft preservation. All APIs/streams are mocked; `E2E_THEME=light` reruns the same checks without Glass.
- `components/FontSettings.tsx` offers separate interface/chat and monospace (code, tool output, terminal) font-name lists in the Fonts & layout section after Appearance, together with chat font size and content width; the Chat section keeps only behavior switches. Every row there has one shape: a header line (label, value, reset button in a fixed 28px column) over a full-width slider, so values and resets line up. A font row puts its name field between label and value, and its slider is the weight (100–600, step 100; `aria-valuetext` adds the weight's name). Both font rows share one grid (`subgrid`), so their name fields start at the same x whatever the labels' widths in each locale. The name field is drawn in the font it names, which is the preview; keep one short section description, no separate preview lines or per-control paragraphs. `hooks/useFontPreferences.ts` stores them only in the browser (`pi-ui-font-family`, `pi-mono-font-family`), applies changes immediately through `--font-ui` / `--font-mono`, and syncs other tabs. AppShell keeps the hook mounted so restoring a font never requires opening Settings or a chat. Empty input removes the override; the original stacks stay in `app/globals.css` as `--font-ui-default` / `--font-mono-default`.
- Font names refer to fonts on the **browser's device**, not the server; no enumeration, upload or remote download. `lib/font-preferences.ts` treats commas as separators, accepts optional enclosing quotes, quotes non-generic names as data, and always appends the default stack. Never interpolate font input into a stylesheet or accept it as executable CSS. Keep raw input whitespace while typing so multi-word names remain editable.
- Each font has a separate base weight (100–600 in steps of 100, default Regular/400; it stops at 600 because headings and labels use 600 and bold text, highlighted bold and the terminal's bold use 700, so a heavier base would outweigh them), stored as `pi-ui-font-weight` / `pi-mono-font-weight` and applied through `--font-ui-weight` / `--font-mono-weight`. Missing/invalid stored weights use 400; saving 400 removes the override. Each reset clears that font's name **and** weight in one update, not the other font or chat size/width. The UI weight is inherited by ordinary interface/chat text; code/pre, highlighted code (including its inline theme styles), source-view line numbers and diffs use the mono weight. Headings, Markdown bold/inline code inside emphasis, and other explicitly weighted labels keep their original weights; do not blanket-override them with `!important`.
- General's Sidebar section (after Chat) chooses where the desktop sidebar shows the file browser: below the sessions (default) or in a tab of its own, as two options in the send key's look (`settings-send-mode-option`), with "Phones always use tabs." under them (`aria-describedby`; `.settings-chat-options + .settings-general-description` turns a section's introduction into a note under its options). `hooks/useFilesPlacement.ts` keeps it per browser (`pi-web:sidebar-files-placement`; anything but `tab` reads as `below`) through `useSyncExternalStore`, so the server and hydration render `below` and the stored choice follows; it follows another tab through `storage` events and reads the key again when a first consumer subscribes, since nobody listened meanwhile. A blocked storage still applies the choice for the page. `SessionSidebar` reads it too and switches live, without remounting the explorer or the tree (sessions.md, the toolbar row and the two layouts); on a phone the choice is kept but the tabs show.
- General's Chat section ends with the switch for pi's own `showCacheMissNotices` (#1265), saved in the global settings.json through `/api/cache-miss-notices`, not in the browser: the notices come from the server, and the pi CLI reads the same key. Its note says a project's `.pi/settings.json` can override it. After a save the open chat remounts (`onSessionReloaded`) to show or drop them; see sessions.md, Cache and cost notices.
- ChatInput remeasures an existing draft when the interface font or weight changes. TerminalPanel subscribes in its existing lifetime effect, updates xterm's family and normal weight (its bold stays xterm's default 700, above every base weight) and refits, never restarting the terminal or its SSE stream for a font change.

## Liquid Glass optics
- Both palettes share the material/layout rules (`html[data-theme^="glass"]`) and runtime, not two renderers. Dark glass now follows a restrained base/elevated hierarchy: neutral smoke base, progressively lighter control/sidebar/overlay fills, soft-white text, neutral selection washes, limited pale-blue action emphasis and subdued silver edges. The former lavender/amber corner treatment is no longer the visual identity. Its lighter raised-grey tint uses an 86% overlay fill to clear AA even over white content, with a 28% scrim. This takes inspiration from Apple's depth and restrained-tint principles, not an implementation of native Regular/Clear: our CSS fills do not analyse backdrop contrast or independently flip light/dark appearance. The `html[data-theme="glass-dark"]` palette selector must match `html.dark` specificity, just as the other dark palettes do. Local overlay accent and terminal chrome colour-scheme follow palette tokens; xterm's own opaque palette is unchanged. The theme catalog drives first-paint restoration and `.dark`, so an explicit Dark glass choice stays dark even when the OS is light.
- Both Glass page grounds keep **colour and grid together**: two static, low-alpha edge washes over the unchanged seven-layer grid. Light keeps blue/purple; Dark glass keeps only near-neutral, barely tinted ambient washes. Its rendered pixel check bounds the corner colour spread and brightness change, preserves the original grid, and checks increasing composited brightness from base to control to sidebar to overlay. `globals.css` exposes that same stack as `--page-grid-image/size/position`, leaving other palettes' paints identical. The wash must tint the grid's opaque paper mask rather than sit invisibly underneath it; it stays behind UI, not on content cards or `.pi-grid-surface` reading areas. No new pattern, animation, photo or request. Reduced transparency/contrast/forced-colour preferences remove both washes and ruling. `e2e/glass-palettes.mjs` compares actual wash-on/off pixels, verifies the retained grid, AA over black and white, both settings, scheme/reload, drafts, dialogs and solid fallbacks at 320/390/1440px; run the left/session-surfaces suites with `E2E_THEME=glass-dark` too.
- Secondary surfaces are included, not just the main composer: `[data-session-search-bar]`, `.terminal-panel-header` and `.workspace-panel-header` use clear material; portaled `.pi-topbar-panel` uses the stronger frosted overlay. Inner prompt/tools sheets stay transparent, the tools sidebar uses one wash, and the mobile toolbar's action strip adds no second blur. Search fields use inset control corners; terminal glyphs keep their own opaque palette. See sessions.md for the fixed-containing-block bug and client-platform.md for terminal lifetime checks.
- `components/LiquidGlassEffects.tsx` is a null-rendering client entry mounted inside `AppShell` / `RobinShell`, after that workspace hydrates, **not** by the streaming root layout. The root effect could run before AppShell's chunk hydrated, writing `data-glass-refraction` and inline styles into server HTML and causing React attribute mismatches. Keep CSS material available for first paint; do not hide this race with `suppressHydrationWarning` or a timer. The left-surfaces E2E also asserts no hydration console errors. It activates `lib/liquid-glass.ts` only for Glass in Chromium (not CriOS), with SVG backdrop-filter syntax support. Safari/Firefox retain the two CSS materials without displacement: `CSS.supports(url(...))` alone cannot prove that a browser renders SVG backdrop filters. Reduced transparency, more contrast, forced colors, hidden tabs, leaving Glass and unmount all stop/release the runtime; reduced **motion** does not disable this static effect.
- `lib/liquid-glass-map.ts` uses the approved study's rounded-rectangle distance/normal field and smooth inward lip (`sin(πt)^0.7`), peaking inside the bevel and neutral at the edge/centre. It is an optical approximation, not the former quarter-circle Snell profile. R/G encode sampling offsets; the centre/outside remain neutral. The 36px displacement scale is reduced for narrow controls so sampling stays within their bevel width. This is the displacement-map approach explained by [Kube](https://kube.io/blog/liquid-glass-css-svg) and demonstrated by [rdev](https://github.com/rdev/liquid-glass-react), not copied component source. `feDisplacementMap` samples the real browser backdrop, never filters foreground controls or captures/clones DOM. No extra dependency, GPU canvas renderer, pointer animation or background screenshot pipeline.
- Each surface has its own size/radius-specific map (each axis ≤256 px, raw buffer ≤256 KiB). Clear surfaces soften the source 0.7px; frosted panels use 10px and 55% displacement strength. Only short clear controls (height ≤120px, area ≤160,000px²) use the study's subtle three-channel dispersion; large composers and frosted panels use one displacement pass. No global saturation boost. Geometry keys include material; class and navigation-placement changes update it even without a resize. Rebuilds wait 100ms for resizing to settle; moving a drawer does not rebuild geometry. A decoded PNG is installed before the old SVG filter is released; `feImage`'s own load event is unreliable in Chromium. The controller observes newly mounted element subtrees, not streaming text, and skips hidden/inert/nested material surfaces. Unmount releases observer targets and filter nodes; no permanent frame loop or snapshot cache.
- `data-glass-refraction` and `--glass-refraction` are runtime-owned decorations only; React never remounts the surface, so editor value, focus and selection survive. CSS scopes the filter override to Glass and immediately disables it for accessibility preferences before observer cleanup runs. The theme catalog/swatch has no second renderer setting.
- `lib/liquid-glass-map.test.mjs` tests neutral centre, inward/symmetric edges, bounded allocation and invalid geometry. `e2e/glass-theme.mjs` uses rendered stripes with the **same** blur/tint/shadows and compares only nonzero vs zero displacement: the rim changes, the centre does not. It also checks clear/frost role selection, horizontal/vertical navigation changes, same-size material replacement, resize replacement, dynamic mount/removal and cleanup on theme/preference changes. `E2E_GLASS_FALLBACK=1` exercises the non-Chromium gate using a Safari UA in Chromium, **not** actual Safari rendering. Real iPhone GPU performance remains a device check; do not infer it from desktop screenshots.

## Robin dashboard settings
- `/dashboard/settings` uses `components/robin/SettingsPanel.tsx` with its own CSS module: a system/UI-font, grouped settings surface, not the Chat settings modal. Desktop uses a scrollable category sidebar and independent detail scrollport; below 960px one native grouped select replaces the sidebar and the page scrolls as a document. Local Appearance/Language stays first and works when the settings API is unavailable; credential storage/privacy text is under Privacy & storage, not the first screen. Colours/radii stay on the existing theme tokens. Non-Glass stays opaque; Glass uses a transparent page ground, 12px outer gutters, separate 30px frosted sidebar/cards, and inset translucent fields/actions. The shared content scrollport has no filter, so cards never sit inside another blur. Material tokens supply solid accessibility/no-filter fallbacks.
- The category sidebar uses 48px inset rows, consistent 32px quiet icon tiles and a neutral raised selection; only the current icon gets the same green semantic colour as enabled switches, never a solid blue tile. Chevrons appear only for the current or keyboard-focused category. Glass reuses its existing active fill without another blur; mobile retains the native select.
- Categories are native fragment links, with `aria-current`; `#notifications` and `#cold-reach-email` remain valid. History/refresh selects the category, unknown fragments use General. Hide inactive panels without unmounting them so switching categories preserves credential drafts. Scope `[hidden]` explicitly so flex utilities cannot expose hidden panels or Telegram-only fields. Category changes clear the previous success receipt; save errors focus a visible alert, and failed transcription-key saves retain their input. API contracts and write-only secret handling are unchanged.
- Settings refreshes reconcile each editable field against its last acknowledged snapshot, never replacing another category's dirty draft or an edit made during a save. Only fields actually submitted are acknowledged; write-only secrets clear only if they still equal the submitted value. Dirty state and unconfirmed writes install `beforeunload` without persisting secrets; entry/exit must remain native, including More's Settings link, so cross-document Back is protected. Hash/category changes keep the mounted drafts and need no warning. Settings reads and writes have 30-second deadlines; a lost write receipt is explicitly uncertain, never automatically replayed. A failed status read after a confirmed save reports that distinction and offers a read-only retry. Retry retains the uncertainty/error until the replacement read succeeds; clearing it before awaiting `load()` falsely suggests reconciliation already completed and races the dirty-state receipt. Tests in `e2e/robin-settings.mjs` include cross-category saves, in-flight edits, cancelled navigation/reload and uncertain receipts.
- Shared `ThemePicker` and `NavigationPlacementSetting` remain the sources of truth. Language uses native radios (including arrow keys); schedule switches are labelled native checkboxes with switch semantics and a forced-colours fallback. Controls are ≥44px, mobile inputs ≥16px, reduced motion removes decoration, high contrast strengthens boundaries. Telegram credential removal belongs with Telegram, not Voice notes. `e2e/robin-settings.mjs` mocks all application APIs and checks history/deep links, retained drafts, failed saves/retry, labels, switches, four themes, 320–1440px, landscape, enlarged text and offline preferences. Also run `e2e/notifications.mjs` and `e2e/navigation-placement.mjs`. These browser checks are not an iPhone hardware test.

## Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package install, remove, update, enable and disable; disabling writes empty `extensions/skills/prompts/themes` arrays to the package entry. Every POST drops the provider routes' shared runtime, since a package can add or drop a provider ([models.md](models.md), Auth and model config).
- `/api/skills` lists through `DefaultResourceLoader`, so settings paths, package skills and project `.agents/skills` appear as the runtime sees them. The loader takes `noExtensions: true` (`lib/skills-service.ts`, #1226): extensions add skills only through `resources_discover` at `session_start`, which a listing never runs, so importing them added nothing and blocked the event loop on every Skills open, skill click and slash-palette open. Skills an extension discovers never showed there, before or since. Even an empty extension load re-keys the SDK's one-cwd factory cache, so a listing for a folder other than the running sessions' still makes their next start re-import. The detail pane lazily reads a selected skill through `/api/skills/content` and renders its post-frontmatter instructions as Markdown; that route permits only an exact file path returned by the same runtime loader and caps the regular-file read at 1 MiB, rather than becoming a general Markdown-file reader. Toggling a skill edits only the `disable-model-invocation` frontmatter key of its `SKILL.md`, so user formatting survives, and `PATCH /api/skills` edits only `.md` files (its roots also hold `auth.json`, settings and project files). `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run in the selected cwd.
- **Skill documents.** A local link in the instructions (`MarkdownBody`'s `onNavigateLink`) opens that file in the same Instructions field. `resolveSkillLink()` resolves it from the linking document's folder, as pi resolves a skill's relative paths; `SkillDetail` keeps a stack of the documents opened, the last one shown under one Back button and its relative path. Switching skills remounts `SkillDetail`, emptying the stack. A forward link brings the field's top, or the `#heading`, into view once the document shows. Before leaving a document, save the `.config-detail` offset in the detail's local map; Back restores it after the Markdown arrives, instantly, and focuses the Instructions field with `preventScroll`. The map dies on switching skills, not on following a link. `e2e/design-continuity.mjs` checks position and focus with a delayed document render. A link to the skill file itself reads it without `document`. The client refuses nothing: an absolute path or a `..` past the folder goes to the route, whose message shows under Back.
- `/api/skills/content`'s optional `document` is a path in the loaded skill's `baseDir` (pi's dirname of the skill file): relative, without `..`, `\`, `:` or NUL, `.md`/`.markdown` by name and by real path, inside the folder after symlinks (`isExistingPathWithinRoots()`), a regular file up to 1 MiB. One stat before the bounded read answers a FIFO or a directory with 400 and a larger file with 413; a missing file is 404, a link out of the folder 403, and no refusal or failed read names a path. Without `document` the route reads the loaded file exactly as before.
- **Group switches.** Each sidebar group of the Skills, Plugins and MCP panels (a skill scope, a package scope, an `mcp.json`; not standalone extensions) has a `ConfigSidebarGroupSwitch` in its heading row, so the 190px phone sidebar loses no height. As with the Models provider switch, it is on only while every row is: a partial group reads as off beside its `n/m` count and one click completes it. A panel whose group can hold rows its switch never turns on passes its own `checked` (MCP: `mcpGroupSwitchChecked()`), or the switch stays off for good. One request carries the list (`PATCH /api/skills` `filePaths`, `POST /api/plugins` `packages`, `POST /api/mcp` `set-enabled` `servers`) and answers per item, so a refused row does not stop the rest; what was left undone shows under the heading (`ConfigSidebarGroupStatus`). An entry already in the requested state is left alone; enabling keeps an entry's own keys such as `autoload`. `SettingsManager` never throws a failed load or write (`flush()` resolves), so the bulk plugin path reads `drainErrors()`, or an unreadable settings.json would report success. Disabling empties the four resource lists and keeps no filters, so a group switched off leaves an enabled filtered package on (the SDK reports every object entry as `filtered`) and says so; the bulk route refuses it.

## Shared blocks
- Enabled switches use the theme's green `--success`, not the navigation/action `--accent`, in both Chat (`.config-switch`, including hover) and Robin settings. Their knobs use `--bg` for light/dark contrast; off states and focus rings are unchanged.
- Configuration controls/captions use `--config-caption` (1rem, 13px at the default root), body copy `--config-copy` (~14px), headings ~16px and `--font-ui`; explicit code/path mono and Markdown prose remain unchanged. Footers wrap rather than squeezing text. Touch controls reach 44px. A successful Save is a quiet receipt, not a pop/check-draw/shadow animation; error text stays visible and Models marks it as an alert. These rules live in `app/settings.css`, not per-panel font overrides.
- Panels are built from the shared blocks in `components/SettingsUi.tsx` (`ConfigScopeTag`, `ConfigScopeSwitch`, `ConfigSaveTarget`, `ConfigAddSourceHeading`, `ConfigAddSourcePanel`, `ConfigDetailGrid`, `ConfigFooterStatus`, `ConfigTrustNotice`), `itemsToSwitch()` in `components/settings-ui-helpers.ts`, and `lib/display-path.ts`; a new settings section reuses them instead of copying a panel. `SettingsUi.tsx` takes every word as a prop and holds no state, so it renders outside the i18n provider; panels pass `t()` strings.
- **Every add pane chooses global or project in one place:** a `ConfigSaveTarget` (scope switch aria-labelled `config.saveTo`, plus the path that choice writes to) first under the pane's title, where a detail pane shows its `ConfigScopeTag` and path. Skills, Plugins and MCP get it through `ConfigAddSourceHeading` (title, the catalog links at its right, then the save target); Sub-agents put it in the detail header in place of the tag while creating. The submit button stays where its flow needs it (Install under the source box or on each skill result, Save in the footer, Add at the end of the MCP form), with why it waits beside it, not under the save target. The path is shown whole, never cut short: it wraps after a separator (`<wbr>`), then anywhere. Sub-agents offer both scopes whatever the folder's trust: profiles are not project resources that wait for it.
- **Why a control is unavailable is visible text** — a scope switch's `disabledReason` (under the switch's whole line, so controls passed as its `children` stay level with it), the note under a detail header, a footer summary that opens its diagnostics — never only a `title` tooltip, which a touch screen cannot show.
- `ConfigTrustNotice` shows its button only when given `onTrust`; Settings › MCP passes AppShell's trust dialog through `SettingsPanel` (see **Trust from Settings** in [mcp-settings.md](mcp-settings.md)). Skills and Plugins take the page's `trust` and reload after a decision but have no Trust button; adding one needs `onOpenTrustDialog` passed to them and `mcpProjectTrustable()`'s rule.
