# Research workspace

`/research` is a general research workspace, not a HEAT page and not a PDF manager. The unit is a **research project** (课题): what you are trying to find out, what you are doing about it this week, what you have learned, and the papers and discussion gathered for it. HEAT is one project among any number.

## Research home

`/research` opens the **research desk**. A left filing rail holds Home, active projects, New project and an explicit Archived disclosure (including an empty state). Archived projects remain accessible without reappearing in the active list. Its default surface shows active projects with their question, weekly goal, paper count and notebook presence; a secondary reading queue sits alongside. **Papers** holds the full library, with independent project and human reading-status filters, title/author/tag search and catalog search. The project selector includes archived projects. A home prompt opens papers not yet assigned to a named project; filing still happens through the existing paper membership control, never automatically. **Assistant discussion** still accepts a local PDF, paper link (arXiv, DOI, PDF), or general question without a project: the agent gives a detailed standalone explanation with examples, evidence and limitations. Conversation deep links open the assistant surface unless an explicit `view=overview|papers|assistant` selects another surface. From a paper's sheet, "Add to a project…" files it into a project. The home is a reserved project `general` in `research-projects.json` (never a tab, never archived or renamed); its readings save no project connection, and `research_relate` refuses it. `/research?project=<id>` opens a project tab.

### Project editor safety

`ProjectDialog.tsx` compares drafts with its opening snapshot. Cancel and Escape close clean editors immediately; changed editors require explicit discard confirmation. Archive/restore also confirms before discarding edited text—it is not an implicit text save. A synchronous request guard prevents duplicate submits and dismissal while saving; fields stay readable/copyable but read-only, and visible status explains the wait. Failure leaves the draft editable for an explicit retry. A native before-unload warning covers dirty/pending editors, not guaranteed recovery after mobile process termination or a general SPA navigation guard.

Desktop initial focus goes to the name; narrow/coarse-pointer modal openings focus the heading before `showModal`, avoiding an input-focus/blur keyboard flash. Inline setup never autofocuses. Cleanup explicitly returns focus to a still-connected opener. Escape is intercepted before the native close-watcher because repeated native cancel requests can become non-cancelable even when a discard prompt was declined. Native cancel events use the same guard.

Checks: `components/robin/ProjectDialog.test.mjs` and `e2e/project-dialog.mjs` cover clean/reverted/dirty forms, discard cancellation, archival, same-tick repeated submits, pending Escape, failed save/retry, and desktop/emulated-touch focus. Browser writes are intercepted fixtures; real phone keyboard behavior and concurrent editing from other tabs are not established by these checks.

## Direct PDF upload

- **Upload PDF and read** is in the conversation composer on home and every project, even with an empty library. A native file picker works on desktop and phones; no public URL or pre-existing paper is required. The project focus/notebook is flushed before import.
- The existing bounded source endpoint accepts `{ file, projectId }` multipart data when no `id` is supplied. `importResearchPdf` validates the project, byte limit/header and usable extracted text before publishing one complete record. Original bytes use the existing content-addressed PDF store; exact duplicates reuse the paper and merge project membership without replacing notes, evidence or readings. Invalid, scanned-without-text, encrypted or cancelled extraction does not create a placeholder paper. The limit remains 20 MB / 400,000 extracted characters, with truncation reported; OCR is not added.
- A local-only paper has `url: ""`, filename-derived title, `provider: "Uploaded PDF"` and the retained `source.pdfHash`. Public URL validation is unchanged. Reading by paper ID uses the saved source; preview/download, summaries, notebook capture and exports work without inventing an external source link. Home uploads are unfiled; project uploads join that project. No storage migration/backfill or automatic catalog identification.
- On success the UI starts the existing paper-scoped reading turn and selects its conversation. If another run is busy, the conversation is archived, or starting the model fails, the PDF stays saved with an explicit **not started** notice and an Open action; use **Read it for me** to retry without re-uploading. Changing conversations/projects during extraction cannot send a late reading into the new selection. Accepted model work still survives navigation as before.

## Candidate discovery

The dedicated search bar on home and project pages searches arXiv, Crossref and Semantic Scholar without starting a model turn. Blank project searches use recognised public research concepts from the brief/current focus; keyword ranking, deduplication, year/venue filters and visible source failures produce a reviewable shortlist. Google Scholar is a labelled manual supplement. Candidates enter the library only on **Add and open**; reading remains a separate action. See [Project-aware paper discovery](research-paper-discovery.md) for privacy boundaries, ranking rules, limits and source research.

## What a researcher needs, and where it lives

| Need | In the workspace |
| --- | --- |
| Several lines of inquiry, switched quickly | Text project rows in the left rail (at the top on phones); each keeps its own focus, thread, papers and notebook. `+ New project` asks for a name and "What are you trying to find out?" |
| The agent should know what I'm after | The **brief** (project dialog) and **This week** (editable in Overview, autosaved). Both are read on every turn; a turn drains pending edits first and refuses to start on a failed save. |
| Find and read papers without clicking through steps | Ask a question or paste a link. The agent searches, obtains the PDF, reads every chunk and saves a reading. No Add/Fetch/Read buttons. |
| Know what is waiting on me | **Needs your PDF** in Papers, with a shortcut from the other views: each paper the agent could not obtain has source/PDF links and an **Upload PDF** button. An upload opens the assistant surface and asks it to read. |
| Understand a paper and ask about it | The paper sheet: reading on the left (abstract explained, summary, connection to each project, original abstract, full text by page), **Ask about this paper** on the right with quick asks (explain simply, walk through the method, weaknesses, use it in my project, quiz me). Answers belong to the selected paper conversation, also accessible from the workspace's conversation list. |
| Keep conclusions | "Keep in notebook" under an answer appends the stored answer and original source links to the project notebook AND archives that answer as a new Markdown note in Obsidian. The notebook downloads as Markdown. |
| Organise readings in Obsidian | Paper sheet → Save to Obsidian: preview, choose a vault, confirm. Front matter carries `projects: ["[[Project]]"]` and a project tag, so the vault groups readings by project. |

Design choices:

- `useResearchReader` owns shared home/project paper loading, accepted-turn URL changes, conversation selection and upload-triggered reading. The pages retain only their layout, library filters and project notebook. Conversation changes flush pending project notes, late reads/navigation completions cannot restore an old selection, and cross-project links retain their paper/conversation parameters while the parent saves the departing project.
- One selected conversation per workspace, with the paper sheet showing that same conversation beside its source. The project discussion, each paper's default reading, and additional topics have separate histories. The conversation picker shows titles, associated papers, update times and running state—not all message bodies. The old separate detail-page chat is gone.
- Focus/notebook replacement saves carry a content revision and only changed fields. The domain compares the revision under the same project-file lock used by Keep's append; old or unversioned clients receive 409 instead of overwriting newer notes. The workspace notebook retains drafts on conflict and pauses autosave. Copy/download the draft before explicitly confirming a reload and merging it; the draft is not automatically rebased. Project renames do not invalidate the notes revision. No storage migration is needed.
- Overview puts the focus and notebook in one document column rather than squeezing them into a margin beneath the reference bibliography. Papers stacks the library and catalog search with a hairline separator. Only the selected surface is visible.
- The paper sheet keeps a visible top-left Back button in both reading and asking panes. Its non-shrinking header clears mobile safe areas, and the sheet uses `--app-viewport-height` for the installed app/keyboard. Back follows the existing save-before-close path to the current project (or home), not arbitrary browser history; it does not stop a background reading.
- Enter sends, Shift+Enter (and touch keyboards, IME composition) make a new line. Acceptance clears only the submitted composer snapshot, never edits made while sending; both the discussion and paper sheet use the same draft guard.
- Supplying paper text/PDF flushes notes once, saves the source, then starts reading without invoking another stale note save. Source completion advances the note draft's revision while retaining typing during upload; a concurrently changed server note still conflicts.
- Only one research turn runs at a time across projects; another project shows "the agent is working in X" with Stop.

These are design hypotheses from first principles, not results of a usability study.

## Data model

- `research-domain.ts` owns projects in `research-projects.json`: `{ id, name, brief, objective, note, links, reference?, archived? }` plus the active project. Projects are archived, never deleted. `reference: "heat"` attaches the authored, dated HEAT takeover reference to that project's context only.
- **Migration is read-only until the first write**: with no `research-projects.json`, existing `research-objective.json`, conversation or papers are presented as one project `heat` (name HEAT, the four original links). The first write persists it; the legacy files are left in place and no longer read once the projects file exists.
- `research-conversation.json` v2 holds `{ version: 2, sessions, run }`. Each human conversation has an ID, project, optional paper, title, kind, metadata revision, archive state and its own messages/error/stopped state. `run.conversationId` is the human conversation; `run.sessionId` is one underlying Pi execution. These are intentionally different identities.
- Conversation migration is read-only until the first mutation, under the existing JSON lock; that mutation first saves `research-conversation-pre-sessions.json` with exclusive creation. Explicit `paperId` messages retain their IDs and execution references in that project's paper default. Unscoped messages become **Historical discussion**, never assigned by titles or AI links. Legacy in-flight runs retain their owner. Existing paper transcripts and notebook capture receipts are not rewritten; previously trimmed messages cannot be reconstructed. Unsupported schema versions fail closed.
- Papers carry `projectIds`; papers saved before projects (no field) belong to `heat`. New papers start with `[]` and join a project when the agent reads them for it, or via POST `?project=`. "Remove from project" only detaches.
- `analysis.connections[projectId]` holds each project's connection (text, focus at the time, basis "full reading" or "saved reading"). The legacy `heatConnection` reads as HEAT's. A fresh reading keeps other projects' connections.

## Conversation management

1. Opening a paper resumes its default conversation for the current project. Repeated opening never creates duplicates. New conversation creates a separate named topic, associated with the selected paper when there is one; returning to that topic resumes only its messages.
2. The workspace and paper's Ask pane offer a keyboard/touch-accessible conversation picker, title/paper search, new, rename, archive and restore. Lists show metadata only. Archived conversations are hidden from the active list but remain readable through their links and the archive view; restore before sending. Archiving is reversible, never deletion, and refuses a live running conversation. Rename/archive check the metadata revision instead of overwriting another tab's edit.
3. `?conversation=<id>` persists the selection through reload and browser navigation. Scope-mismatched/missing IDs fail visibly rather than falling back to another history. Opening a different paper selects its own default; closing the reader keeps the current conversation. Changing topics inside a paper flushes that paper's notes first. Composer drafts are browser-local and keyed by conversation.
4. A single public URL sent in the default project/home discussion starts a separate reading conversation (or resumes the known paper default). Its initial title is the request. Only a verified matching `research_read` result binds an unknown link to a paper; later source metadata can update its automatic title, never an explicitly renamed title. Multi-paper searches/comparisons stay in the project discussion; obtained/related papers also get default conversations for subsequent individual reading. Explicit custom topics never auto-switch based on links.
5. Every model turn receives only the selected conversation's bounded recent history. Project goals, notebook and saved paper evidence remain shared intentionally. Legacy `Paper.messages` and other topics' chats are not replayed. Model executions remain one-shot; a human conversation is not an ever-growing single Pi execution.
6. The existing single global research-run lock remains. Browsing, searching, renaming and switching conversations do not cancel accepted work. Another conversation shows that the worker is busy elsewhere. Completion/errors/stopped state go to the initiating conversation even after navigation; late polls/POSTs cannot replace a newly selected conversation. Stop carries the observed run ID so an old button cannot cancel a replacement run.
   `useResearchThread` also owns a monotonically increasing read sequence shared by
   polling, manual reload and post-command refreshes. Only the current read may
   publish a snapshot or transport error; a stale success cannot hide a newer
   failure. Accepted POST receipts invalidate earlier reads, and leaving a
   conversation/unmounting invalidates manual reads too (including A → B → A).
   A departing send's cleanup cannot start a read that supersedes the new topic.
   This is browser snapshot ordering, not server cancellation or cross-tab locking;
   the polling cadence and accepted background work remain unchanged.
7. Keep → Obsidian still resolves the original assistant message ID within its project, including archived conversations. No automatic backfill, duplicate capture or reset of the notebook. New conversation history is retained rather than silently dropping messages after 100; model context stays bounded independently.

## Original PDF preview

- The sheet's **Full text** tab defaults to original-layout PDF pages, not extracted text. `PaperPdf.tsx` offers previous/next, page selection, fit-width/zoom and the original download; extracted text stays in a collapsed fallback for selection/accessibility. Pages are server-rendered JPEGs, not a selectable-text PDF.js viewer. This avoids mobile browsers' partial embedded-PDF support and publisher framing restrictions.
- `paper-pdf-domain.ts` preserves new downloaded/uploaded originals by SHA-256 in `paper-pdfs/` under the Robin data directory; `PaperSource.pdfHash` references those bytes. Include this directory in backups: uploaded originals are not disposable cache. Page-count JSON and requested-page JPEGs alongside originals are regenerable. Rendering requires Poppler (`pdfinfo` + `pdftoppm`), has a per-process timeout and renders one bounded-resolution page at a time.
- Existing remote sources are fetched through the bounded, DNS-pinned PDF downloader and indexed in `paper-pdf-downloads.json`, without changing paper revisions, extracted evidence or saved readings. Existing filename-only uploads must be re-uploaded: previous versions discarded their original bytes, and the preview must not silently substitute a different publisher copy. Original files are limited to 20 MB; previews to 2000 pages. Retrieval/render failures offer Retry and Upload rather than showing text as though it were the original.
- **PDF text extracted · N pages** describes extraction only. Displaying original figures does not give the research agent visual understanding; its reading evidence remains extracted text.

## Keep → automatic Obsidian archive

- Each human Keep click sends a saved assistant message ID, not browser-generated Markdown. `research-capture-domain.ts` resolves it within the named project's thread, freezes its answer/date/source links and appends it to the latest notebook before publishing the archive. No model call, tool-triggered capture, automatic capture of every reply, or backfill of past notebook entries.
- The notebook shows the destination selector. A single registered vault is selected automatically; several require a choice. The first capture remembers the project's chosen vault on the server. Files go through Notes' existing `Notes/Robin-<draft-id>/<title>.md` publication with project wikilinks and message provenance, never overwriting an existing note. This writes on the server computer; it does not configure mobile Obsidian sync.
- `research-captures.json` stores capture checkpoints keyed by project + message ID, immutable source snapshots, stable draft IDs, pinned destinations and archive receipts. The file stays in the JSON domain store (not task SQLite runtime state). Checkpoints precede vault publication; retries recover Notes' receipts and preserve external edits. Successful receipts are historical, not proof that the file has not subsequently been moved/deleted in Obsidian.
- The UI restores archived/partial states after reload. If the vault is missing, inaccessible or unsafe, the notebook remains saved and the answer offers **Retry Obsidian archive**. Repeated clicks reuse the same capture, even after the source conversation has been trimmed. A changed vault path fails closed. Failed publication can leave its reusable Notes draft visible until a successful retry.

## Agent

### Paper-first reading contract

- A single paper URL, “Read it for me”, a full-reading request or an upload asks for a **standalone tutorial**, not an abstract-length synopsis: (1) problem and plain abstract explanation with an example, (2) motivation and prior-work gap, (3) the main body—concepts, step-by-step method or study design, inputs/outputs, design rationale, worked example and explained equations, (4) experimental questions, settings, baselines, metrics, results and limitations, then (5) a separate project-relevance section only when in a project.
- Do not open with HEAT advice or interleave project relevance into the tutorial. Preserve detailed explanation in the conversation even if a reading was saved before; a link to that reading is not the answer. Explicit full/detailed readings revisit the source, not just cached summaries. Narrow follow-ups, brief summaries explicitly requested by the user, application-only questions and literature comparisons retain their own scope.
- Existing storage fields suffice: `abstractExplanation` explains the abstract; `summary` holds the detailed standalone walkthrough; `projectConnection` holds relevance and clearly labelled proposals. No schema migration, automatic re-reading, notebook rewrite or Obsidian publication is part of this prompt change. English, Simplified and Traditional Chinese prompts cover home, project, link and upload entries.
- Project context still loads first but is used for relevance after understanding the paper. Distinguish user goals, historical reference facts and AI-generated notebook proposals. Links are not inspected document contents; the dated HEAT reference is not proof of current code/settings. Say when context or a direct connection is missing, rather than forcing an experiment. Paper citations, coverage, illustrative-example labelling and the no-visual-evidence limitation remain mandatory.
- Prompt-contract tests check the actual scoped-turn instructions and all localized entry requests with a stub model, plus the tool schemas. They do not demonstrate LLM teaching quality; that needs a real reading reviewed by the user. Existing answers are unchanged; request a fresh detailed explanation to use the new policy.

### Execution and evidence

- Tools (`ROBIN_RESEARCH_TOOL_NAMES`, exact allow-list): `research_context`, `research_search`, `research_read`, `research_save_summary`, `research_relate`, `web_search`. No filesystem, coding, mail, calendar, objective or vault writers.
- `research_context` returns the run's project (brief, focus, bounded notebook, links), other projects' names, this project's papers, and `elsewhereInLibrary` (papers read for other projects).
- `research_read` adds the paper to the run's project. `research_save_summary` requires every chunk of the current source to have been returned in this session and records `projectConnection` against the focus the agent read. `research_relate` attaches an already-read paper to this project from its saved reading, refusing outdated or absent readings.
- When a PDF cannot be obtained the agent tries legitimate open-access copies, then says which papers it could not get with their links. It never bypasses paywalls or authenticates to publishers. Abstract-only readings are labelled.
- Every research tool publication (candidate cache, new paper, source/PDF, access failure, membership, summary and connection) checks persisted execution ownership and cancellation while holding the conversation lock. Network/download/extraction awaits stay outside that lock. The tool session pins its run; the initiating user message also retains the Pi execution ID so a late first call or reloaded tool registry cannot fall back to the current project after replacement. Progress and final replies reject cancelled/expired work too. Standalone extension sessions without a dashboard run remain supported; completed writes before Stop are kept.
- Reading runs independently of the browser: both agent POST endpoints claim the run synchronously, return `202 { run }`, and execute through Next's `after`. Never pass `req.signal` into the reading turn: a mobile disconnect or proxy timeout is not a request to stop paid work. The UI polls the saved conversation for progress, reply and errors; successful polling clears transient transport errors without clearing a rejected submission. Stop still uses DELETE. This survives page reload/disconnect, not a server-process crash (the existing stale-run timeout allows retry).
- The previous evidence, cancellation, context-bound and storage limits are unchanged (chunked reads with a per-session ledger, stale-source rejection, 10-minute deadline, 12 × 6,000-character history, 20,000-character notebook context with head + tail).

## HTTP

- `POST /api/research/papers/search`: `{ projectId, query, sources?, fromYear?, venue? }` → deduplicated, keyword-ranked metadata candidates, actual queries and per-source status. No model/library/notebook writes. Legacy GET keyword/arXiv/DOI search remains available.
- `GET/POST/PATCH/PUT /api/research/projects`: list with counts (no notebook bodies), create, edit name/brief/links/archived, set the active project. `researchProjectBoard` computes all project counts from one conversation read; adapters do not aggregate/sort message bodies. `listResearchSessions` reads metadata for the picker, and `readResearchRun` supplies execution ownership without constructing a project transcript. JSON is still parsed in full; this is not a cache, storage migration or incremental transcript protocol.
- `/api/research/objective?project=`: focus + notebook (GET/PUT) and append (PATCH). GET `&captures=1` additionally returns capture receipts and registered vault choices. PATCH `{ messageId, vaultId? }` keeps and archives a stored answer, returning updated notes and `captureState` (partial failures have `capture.error`); legacy PATCH `{ text }` only appends. Without `project`, the active one; with no projects, the first write creates a general "Research" project.
- `/api/research/agent?project=&conversation=&paper=`: GET one conversation, its metadata, project conversation summaries and the global run. Omitting conversation selects the paper default (when paper is supplied), otherwise project discussion. POST `{ question, projectId, conversationId?, paperId?, locale }` returns `202 { run }`; DELETE `?run=` stops the observed run.
- `/api/research/sessions?project=`: GET metadata only; POST `{ projectId, title, paperId? }` creates a topic (`{ projectId, paperId?, ensure: true }` resolves a default); PATCH `{ projectId, id, revision, patch: { title?, archived? } }` changes metadata. No delete endpoint. `/api/research/papers/agent` also returns `202 { run }` after validating the paper revision; it no longer waits to return a completed paper.
- `/api/research/papers?project=`: list (needs-PDF rows include `downloadLinks`); `?id=` one paper; PATCH `{ id, removeFromProject }` detaches.
- `POST /api/research/papers/source`: multipart `{ file, projectId }` imports a new local PDF; multipart `{ file, id, revision }` continues to replace an existing paper's source with revision checks. Upload and model start are separate requests, so a rejected turn never loses a successful import.
- `GET /api/research/papers/pdf?id=` returns `{ hash, pages }`; add `&hash=…&page=N` for one original-layout JPEG or `&hash=…&download=1` for the original PDF. The route resolves a saved paper only (no caller-supplied URL/path), refuses changed hashes and invalid pages, and sends images/downloads with private no-store headers.
- `/api/research/link-icon?url=`: the icon of a saved project link (GitHub, Sheets, Docs, Drive, or the site's favicon), fetched once and cached locally; other URLs are refused.
- PATCH `/api/research/papers` `{ id, addToProject }` files a paper into a project.
- HEAT's notebook remains in `/research?project=heat`; the former `/research/heat` editor is retired.
