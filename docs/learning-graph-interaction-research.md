# 学习知识图谱：交互研究与样板

研究日期：2026-10-25。**状态：研究结论与待验证假设，不是已批准的产品规格，也不是已完成的 Obsidian 知识库。**

历史样板（现已按用户要求移除，不再提供页面）：三个方案使用同一小份缓存知识；仅验证导航、关系理解、阅读、比较与作答衔接，不读写真实笔记、不调用模型、不保存进度。正式 `/learn/roadmap` 没有被替换。

## 1. 用户真正要求的是什么

- 按 roadmap.sh 的实际节点与路线建立学习骨架，而不是重新挑几十个概念做另一套课。
- 先对行业、系统各层、概念与工具形成 high-level 认知，再能沿每个节点深入“是什么、为什么、如何工作、怎么做、怎么选”。
- 正文、关联和资料属于 Obsidian；网页是同一知识体系的学习入口，不是第二份硬编码教材。
- 交互本身需要研究：知道全景、知道位置、知道下一步、允许探索、不会迷路，而不是一张漂亮但难以使用的大图。

已有[三条职业路线总览](/obsidian?vault=145be82b55ba948a&note=%E6%8A%80%E6%9C%AF%2F%E8%81%8C%E4%B8%9A%E8%B7%AF%E7%BA%BF%E5%9B%BE%2F00+-+%E4%B8%89%E6%9D%A1%E8%81%8C%E4%B8%9A%E8%B7%AF%E7%BA%BF%E6%80%BB%E8%A7%88.md&view=read)记录了 Full Stack、AI Engineer、FDE 的原站来源，以及“原图节点、教学补充、建议顺序”的区别。这是已有材料，不代表用户已经完成相应学习。此处链接只作研究溯源；产品不能硬编码这个 vault ID。

### Obsidian：全局图、局部图与 Canvas 是不同工具

[Graph view 官方说明](https://help.obsidian.md/plugins/graph)：节点是笔记、线是内部链接；全局图支持筛选与分组，局部图可按连接深度展开。这适合发现关联，但一个 wikilink 本身并不表达“前置”“实现”“替代”中的哪一种。

[Canvas 官方说明](https://help.obsidian.md/plugins/canvas)：支持笔记卡片、分组、带标签的连线、跳到分组、跟随连接、缩放到选中项；文本卡片不会出现在 Backlinks，需转为文件才会出现。

结论：**知识本体要落在 Markdown 笔记；Canvas 引用笔记，负责空间组织。** 不能把全部教材只写在 Canvas 文本卡，或依赖全局连线自动生成教学关系。官方帮助最初未能被正文提取器解析，本次通过浏览器实际加载并读到了上述内容；不据搜索摘要推断未记载功能不存在。

### 概念图与认知负担

[IHMC：Constructing a Concept Map](https://cmap.ihmc.us/docs/ConstructingAConceptMap.php)强调：
- 每个局部概念图应回答一个明确问题。
- 两个概念之间需要能组成有意义陈述的关系词。
- 跨分支关系要有选择，不是把一切相关的东西都连起来。

这是组织知识的理论与方法指导，不是证明本项目某种布局提高学习成绩的实验。

[NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)区分：
- 按层展开：先看到核心，再按需深入。
- 按步完成：沿任务序列向前。
- 当步骤互相依赖、用户需要反复对照时，单向向导会增加导航成本。

[NN/g：Recognition and Recall](https://www.nngroup.com/articles/recognition-and-recall/)支持把需要的上下文保留在可见／可取回的位置，而不是让用户记住先前页面内容。

推论（待用户验证）：**认知探索与顺序学习要共存，但不一定需要两个完全独立的工作区。** 学习界面的“减少回忆负担”不等于练习不能要求主动回忆；导航帮助找路，练习可以隐藏答案让用户先作答。

### 无障碍不是后补

[W3C：Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements)明确拖拽功能应有单指、不拖拽的替代方式；仅有键盘替代还不覆盖全部触屏情形。

因此不把拖动／捏合／悬停作为必经操作。节点有点击、文字关系、明确展开按钮；手机不能把桌面千节点图缩小后直接交付。关系类型有文字，不只靠颜色。

本地 UI 指南检索确认了面包屑、可预期后退与键盘焦点建议。产品样式检索两次只返回通用营销／文档站布局，不符合知识工作区，因此未采纳或保存那些配色和模板。样板沿用 Pi 的纸面、直角、语义色与衬线标题，不引入新的视觉系统。

## 3. 最重要的区分：四种关系不能画成一种箭头

1. **知识归属**：事务属于数据库机制；Redis 是工具。
2. **学习前置**：理解缓存有助于理解 Redis 在缓存场景中的用法。
3. **系统关系**：Redis 可实现共享缓存；缓存失效影响一致性。
4. **路线出现位置**：同一个概念可以在 Full Stack、AI Engineer、FDE 中出现，但学习目标和要求深度不同。

因此“一个概念有一个知识本体”不等于“在所有路线中只有一个位置”。切换路线时应保留当前概念，并告诉用户这个路线为什么需要它，不复制三份容易分叉的 HTTP 正文。

原图上的坐标、连线和排列不是自动生成先修依赖的充分证据。正式整理需保留原始节点出处，另行标记补充说明与教学建议。

## 4. 三个候选，不是三个都要上线的模式

| 样板 | 核心交互 | 擅长回答 | 要验证的代价 |
|---|---|---|---|
| A 路线伴读 | 左侧阶段／步骤，右侧知识正文；有前置与下一步 | 我先学什么，接下来做什么？ | 会不会把关系图误读成唯一线性顺序？ |
| B 关系图谱 | 稳定局部图；单击预览，显式操作才换中心；正文在旁 | 这是什么，与哪些知识有关？ | 图与正文争空间吗？关联会不会分散注意？ |
| C 分层探索 | 领域 → 能力／问题 → 知识点；正文在下方／专注页 | 这一层有哪些东西，各负责什么？ | 横向关联是否被藏得太深？ |

目前倾向的组合假设：**C 做全景入口，A 提供学习主线，B 在需要理解关系时局部展开。** 不把三个方案选择器照搬进正式产品；先观察哪一条操作路径最自然，再收成一个默认体验。

不是默认采用无限力导向图。图只负责说明结构与关系，不能承担全文阅读、所有操作和全部进度。选中节点不应导致其他节点重新漂移；换中心和展开层级要是明确、可撤回的操作。

## 5. 理想的一次学习过程（研究假设）

以“缓存”为样板，不预设用户已懂这个词：

1. 在全景中看见“系统为什么会慢”，知道缓存属于哪个问题域。
2. 进入这一层，先看“缓存是复用结果”与不使用缓存的路径，不先面对 Redis 的命令列表。
3. 看到缓存的几种位置与实现。点击 Redis，只预览定位／用途／边界，不丢失原来位置。
4. 选择深入，展开工作方式、最小示例和验证办法；知识标题旁始终知道自己属于哪一层。
5. 遇到“不一致”，可临时补看缓存失效与数据库事务。返回后恢复原节点、阅读位置与草稿，而不是重回首页。
6. 比较进程内缓存与 Redis，按共享范围、网络、运维、失败边界逐项对照，不依赖记住上一页，也不做缺证据的排行榜。
7. 做一次针对性练习，先给出解释／预测，再逐级提示和参考答案。阅读和选对一题都不自动标记掌握。
8. 回到主线，知道本次补了什么、下一步为何值得学；用户仍可选择自由探索。

“是什么、为什么、怎么工作”应是节点首屏的连续叙述，不强迫读者为了得到基本解释切五个标签。复杂操作、长实验、行业案例按需展开，但必须清楚告诉用户下面还有哪些内容。样板的分区按钮用来试验阅读组织，不是已定稿的 tab 架构。

## 6. 行业认知要进入交互，而不只是附链接

需要区分三类证据：
- **工具定位**：官方文档证明公开能力、接口与限制。
- **公开采用案例**：具体团队在具体时间／场景使用了什么，为什么，付出什么代价。
- **采用分布或热度**：有明确样本和时间范围的调查；不能用 GitHub stars 或一个厂商案例断言“全行业都在用”。

节点展示“概念／机制／工具／协议／应用”等类型；工具放回所实现的能力下面。比较先回答为何需要这一类，再比较工具。没有找到案例就显示“尚未补充公开案例”，不拼出装饰性的“主流”标签。

行业资料会变，基础概念相对稳定；两者各自显示来源与核验日期。案例更新不应默默改写成用户曾经作出的技术决策。

## 7. 正式产品必须提前想清的状态（尚未实现）

- **内容覆盖与学习状态分开**：“待备课／只有概要／有完整说明／有练习”不是“未学／理解／做过”。一个补齐目录的图不能伪装成完成的教材。
- 现有 23 节内容可以迁回对应知识节点，但不能把旧章节自评直接映射成所有相关概念已掌握。
- 搜索中文、英文、别名；结果先显示位置与类型，再定位节点。相同名字不自动合并不同概念。
- 返回、前进、直接打开链接、刷新和切换地图／阅读都要有一致的定位规则。层级父节点、路线位置和浏览历史分别显示，不能拿面包屑假装跨分支历史。
- 返回原文编辑后，网页提示内容版本变化。用户手写内容不被生成流程覆盖；目录／图布局变化不能清空答案。
- 缺少节点正文、来源不可用、文件改名／移走、扫描受限分别给出真实状态；不生成一段通用提示假装有课。
- 手机以清晰的逐层列表／局部关系与专注阅读为主，保留“回到此节点在地图中的位置”；桌面可并排，避免三四栏挤压长文。
- 长按、双击与 hover 只能加速，不承担唯一入口；键盘焦点、返回位置、对话框关闭和触控误操作要有测试。
- 初期不开自动推荐算法、知识点掌握预测或图谱编辑器。先把真实内容、关系和找路做好。

## 8. 怎么验证，不凭截图选赢家

使用同一份有真实解释、不同类型节点与跨分支关系的样板做对照。用户尝试顺序可轮换，避免先用方案学会内容后，让后用方案占便宜。

任务：
1. 找到 Redis，解释它属于什么、解决什么、不负责什么。
2. 找到前置知识，阅读后回到原来的位置。
3. 从缓存失效进入一致性，再沿历史返回 Redis。
4. 对照本地缓存与 Redis，给一个“现在不该引入 Redis”的理由。
5. 给一道练习写一半，切到另一节点，再回来；草稿不丢。
6. 手机上不用拖图，完成以上导航；键盘不使用鼠标，完成节点选择与比较。
7. 明确区分“我看过”“我解释得出”“我做过”，以及“这篇笔记尚未备好”。

记录：找路成功与否、找错类型的次数、返回是否丢上下文、是否反复往返两页比较、能否解释关系、自己的困惑与信心。不以点击数越少越好，不把漂亮截图当学习效果。

自动化测试只证明样板的链接、历史、草稿与布局行为；不能证明学习效果、长期记忆或千节点可用性。上述学习任务仍需要用户实际尝试。
